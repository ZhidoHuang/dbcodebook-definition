# 定义变更影响检查表填写说明

实际机器文件名为当前主题执行目录中的 `definition_change_impact.json`，由 `check_definition_readability.py init-impact` 生成。本说明帮助执行者先把影响想完整，不能用完成后的成果反向补写。

## 1. 先说明这次改变了什么

用普通人能懂的一两句话说明：新增、删除或改变了哪些定义变量，调查对象、周期、问法、组成关系或缺失处理是否变化。不要只写“逻辑优化”“口径调整”或内部状态码。

## 2. 逐个核对改变的问卷题组

| 问卷题组 | 调查时期 | 问了谁 | 官方材料与位置 | 核对过的代表性原题 | 怎样进入定义 | 原题在纯文字稿中的位置 | 结果 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 示例：从父母获得支持 | 2011 | 家庭答题人及配偶 | 2011 家户问卷，第 X 页，题号 XX | “过去一年……” | 判断是否获得并计算金额 | 摘要导读 > 2011 年 | 待核对/通过 |

能够逐字核对时填写原题，并确保相同文字实际出现在正式成果目录的 `文案.md`。只能确认题意、无法核到逐字原题时，填写大白话概括和不能逐字引用的原因，不使用引号。

## 3. 核对所有受影响的读者表面

| 检查面 | 需要回答的问题 | 结果与证据 |
| --- | --- | --- |
| 标题与摘要 | 最终变量数、变量关系、来源组成是否同步？ |  |
| 问卷原题 | 每个新增或改变的问卷题组是否展示了核对过的代表性问题？ |  |
| 定义表与变量顺序 | `Definition / Criteria / detail` 是否覆盖全部分析变量，名称、顺序和显示内容是否同步？ |  |
| Criteria | 每个变量的对象、赋值、跳题、缺失和冲突处理是否完整？ |  |
| 小book提示 | 是否只保留同时影响多个变量或整个主题的重大边界？ |  |
| 公开 R | 代码顺序、业务解释和代表性原题是否与实际实现一致？ |  |
| mapping 与 codebook | 原始来源、分析变量、Label 和 Easy.label 是否一致？ |  |
| 定义卡、图表与附件 | 显示名称、顺序、列数和文件是否同步？ |  |

未受影响的项目也要写明原因，不能空着或只填 `PASS`。

## 4. 停止条件

出现以下任一情况时不能进入正式生成：

- 新增问卷题组还没有核对询问对象、时期或原题；
- 核对过的原题没有写进纯文字稿；
- 任一受影响表面仍未检查；
- 仍存在没有裁决的来源、合并、缺失或冲突处理问题；
- 检查表是根据已经生成的笔记事后补写，而不是在正式编码前同步形成。
