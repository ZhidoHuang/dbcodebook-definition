# dbCodeBookr 函数与用户材料规范

版本日期：2026-08-27

适用范围：所有数据库变量定义任务，包括 CHARLS、ELSA、HRS、NHANES 等。

正式源说明：本文件位于 Skill 仓库 `references/rules/common-materials.md`，是跨数据库用户材料规则的唯一正式来源。其它文件只保留按需引用，不维护可独立修改的副本。

## 0. 先按这 5 步做

下面是每个定义任务都要遵守的主流程。后面的详细规则只解释这 5 步中遇到的具体问题，不再另设一套写作流程。

1. **确认事实和定义方案。** 先弄清调查问了谁、问了什么、各周期有什么变化，最后要得到哪些变量，以及跳题、缺失和矛盾回答怎样处理；同时确定每个来源的完整身份、最终下载别名和合并关系。尚未确定的地方继续查证或交给用户裁决，不能边写成品边猜。
2. **先写一份不带样式的读者文案。** 在当前主题的正式成果目录建立固定文件 `文案.md`，先写出摘要导读、小book提示、全部 `Criteria` 和参考资料说明。这里只写读者需要看到的事实和解释，不加颜色、卡片、HTML 或其它展示代码。`文案.md` 是正式成果的一部分，不放在执行记录目录，也不使用“草稿”文件名。
3. **先把这份文案真正读懂。** 从头到尾读一遍，检查事实是否准确、普通读者能否复述、相邻段落是否自然衔接。发现结构不顺时整段重写，不在坏结构上不断补句子。`文案.md` 没有读顺以前，不得编写用于生成读者材料的文字，也不得运行正式 R。

这里所说的“文案审核”固定指审核主题成果目录中的 `文案.md`，不指已经拼装的最终笔记、网站页面、公开 R 或附件。审核必须覆盖 `文案.md` 的全部内容，而不是只看本轮刚修改的段落。审核通过后，默认继续把修改同步到正式生成源、重新生成和核对成果，再进入网站检查同步阶段供用户实际检查；不要在“审核、修改、生成、网站同步”之间逐步停下等待重复确认。只有用户明确要求“只审核、不执行”时，才停在 `文案.md`。网站更新表示进入用户检查阶段，不表示任务已经得到用户认可或正式完成。
4. **按已经确认的方案编写代码。** 正式 R 按业务顺序实现定义；公开注释必须和相邻代码一起写、一起检查。代码不能承担临时探索和现场决定口径的任务，也不能脱离代码预写一套注释。
5. **生成后再读最终成品。** 样式层只添加颜色、链接、卡片、标签页和展开收起，不改正文。生成后核对可见文字与 `文案.md` 一致，再按网站中的真实阅读顺序通读完整笔记和公开 R。通过后进入网站检查同步阶段；同步网站表示交给用户检查，不表示主题已经完成。

### 0.1 定义变更影响门

新主题，或既有主题新增、删除、重命名分析变量，改变调查对象、周期、问法、计算组成或缺失处理时，必须在编写正式 R 前建立 `definition_change_impact.json`。先运行 `check_definition_readability.py init-impact` 生成检查表，再用大白话填写本次改变了什么、会影响哪些读者材料和数据成果。人类可读填写说明见 [change-impact.md](../../templates/change-impact.md)。

检查表不是完成后的变更摘要。每个新增或改变的问卷题组都必须在正式编码前记录：调查时期、询问对象、官方材料位置、核对过的代表性原题、这道题怎样进入定义，以及原题写在正式成果目录 `文案.md` 的什么位置。官方材料无法核到逐字原题时，只能填写大白话概括和无法逐字引用的原因，不得放进引号冒充原题。

检查表同时覆盖标题与摘要、问卷原题、定义表与变量顺序、全部 `Criteria`、小book提示、公开 R、mapping/codebook、定义卡与图表。未受影响的部分也要写明为什么不受影响，不能留空。检查表仍有待处理项，或核对过的原题没有实际出现在纯文字稿时，不得进入正式生成。

`check_definition_readability.py check` 必须验证当前检查表、纯文字稿、作者全文审核和四份正式成果属于同一版本。网站同步任务开始时还必须运行 `verify-ready`；它只复核现有发布许可，不生成或修补任何审核文件。复核失败时不得绕过。同步完成后进入用户检查阶段，只有用户确认后才算完成。

## 1. 规则边界

- 本文件是跨数据库通用代码与用户材料规则的唯一来源。数据库流程只补充该数据库特有的检索入口、身份键、周期、文件族、特殊编码和数据事实。
- 全部正式规则、数据库事实和填写模板的职责入口见 `规则材料索引.md`。该索引只帮助定位唯一正式来源，不新增或复述具体规则。
- 适用顺序为：用户最新明确裁决 > 本通用规范 > 数据库专属流程 > 数据库 profile。各层只处理自己的职责，不用“优先级”掩盖职责重叠。
- 主题事实以当前正式业务代码、实际 raw 取值与标签、正式 codebook、官方材料和明确裁决为准。已完成主题不能反向产生公共规则。
- 正式分析变量的分类编码默认使用英文/ASCII；中文用于注释、`Criteria`、QA 或笔记解释。只有用户明确要求时才使用中文正式取值。
- 面向读者的公开 R 注释、`Criteria` 和笔记正文不把产出称为“正式变量”。说明本次构造或解释的概念时使用“定义变量”，说明进入 `analysis_db` 的数据列时使用“分析变量”；“正式变量”只用于内部流程状态或技术约束。
- QA 可以记录覆盖率、缺失、冲突、内部来源和技术假设；用户材料只保留理解和使用变量所需的事实。

### 1.1 通用命名

- 变量名在含义清楚的前提下保持简短，优先使用领域内稳定、容易辨认的共同前缀和词干。
- 命名前检查已有正式变量系列；存在明确系列关系时复用共同前缀，并一次性确认相关变量是否需要同步命名。
- 不把处理步骤或解释性长句塞进变量名，也不能删掉区分即时/延迟、状态/数量、单项/汇总等含义所需的核心维度。
- 数据库或主题已经裁决的前缀可以继续使用，不机械复制到其它数据库。

### 1.2 来源别名必须在下载前确定

- 先确认来源身份和研究关系，再决定别名。只有题义、编码和适用对象一致，并且在不同调查时期互相补充的直接来源，才使用同一词干和 `_1`、`_2` 等顺序后缀。顺序同时表示正式合并时的优先级，必须在下载前写清。
- 预载、上一轮回答、代理回答、补充模块、外部派生或其它身份不同的来源使用能说明身份的语义后缀，不混入直接来源的顺序组。不同文件或模块中的同名变量必须设置能够区分来源的唯一别名；当前来源清单中没有重名冲突的变量保留原变量名，不额外添加文件或模块后缀。
- 按成员编号重复展开的变量按完整变量族处理。只要其中一个成员需要调查时期、模块或来源后缀，整组成员都使用同一后缀；不得只给发生重名的个别成员改名。完整别名模式和编号范围写入 `definition_search_record.json` 的 `alias_families`。
- 最终别名在 dbCodeBook 页面选择变量时设置。重新下载后的 `raw_data.csv` 和 `raw_codebook.csv` 必须直接带有这些别名；不得下载后修改 CSV 表头，也不得在正式 R 中复制、改名或按列位置制造别名。
- 正式 raw、codebook、公开 R、mapping 和完整定义链路保留每个来源的完整别名。面向读者的紧凑来源图可以把已经核实属于同一组的重复成员合并成范围标签，但该标签只用于展示，不能反向改变正式来源清单。
- `definition_search_record.json` 记录来源关系、最终别名和变量族；数据库专属流程负责规定页面选择清单、预览检查、下载与恢复方法。记录模板和任务卡只保存本次事实，不另立命名规则。
- 最终手动选择的来源字段必须至少承担一种明确作用：参与定义、作为辅助判定条件，或执行本主题实际需要并会报告结论的验证。仅用于“顺便保留”“可能链接”“标记来源版本”而未在当前主题使用的字段不得纳入。平台自动提供且正式输出必需的记录键单独管理，不用无关业务字段代替记录键。

### 1.3 三类内容不要混写

- **摘要导读、小book提示、`Criteria` 和参考资料说明**先写纯文字，详细要求见第 5、6 节。
- **公开 R 注释**跟着对应代码写，详细要求见第 2 节。
- **展示样式**最后添加，不能参与写作。

`文案.md` 至少按 `## 摘要导读`、`## Criteria`、`## 小book提示`、`## 参考资料说明` 分成四部分；`Criteria` 下再按最终定义变量逐项列出完整文字。没有小book提示时，在文案中写明“本主题没有需要单独提示的主题级边界”，正式笔记中省略提示卡。参考资料说明必须逐条写清材料支持的事实和不支持的项目处理，不能等生成笔记后再补。

如果本次只返修其中一类内容，开始前必须写清允许改什么、禁止改什么。不得因为这些内容最后出现在同一篇笔记中，就顺手改动其它文字、代码、变量或样式。

## 2. 正式 R 与公开代码

### 2.1 公开边界

正式 R 中 `# 输出` 之前是用户会看到和复制的公开代码，保留从读取数据、理解原始结构、定义变量到正式输出的主线；`# 输出` 之后放 QA、HTML、detail、笔记拼装和可视化等后台代码。

公开区应包含：

- 环境、包和 raw 读取；
- 必要的真实取值查看、清理和重编码；
- 跨周期来源合并、回溯和正式变量构造；
- `map <-`、`add_mapping()`、字典和四张正式工作簿的生成与写出。

每个正式分析变量都必须通过 `add_mapping()` 登记全部参与定义的 raw 来源，并由 mapping 驱动 codebook 的 `original_vars`、`processed_vars` 与 `count`；不得直接手填绕过。CHARLS 保留完整模块来源身份，ELSA 保留完整 `Variable (File)` 身份。

后台区包括 QA 汇总、批量标签扫描、哈希/覆盖核对、HTML/笔记生成和只服务展示的 helper。笔记公开代码默认截取到 `# 输出` 之前。

### 2.2 头部模板

```r
rm(list = ls())

for (pkg in c("devtools", "openxlsx", "dplyr")) {
  if (!requireNamespace(pkg, quietly = TRUE)) {
    install.packages(pkg)
  }
}

library("devtools")
library("openxlsx")
library("dplyr")

install_github("ZhidoHuang/dbCodeBookr") # 提示更新包, 可选3跳过，首次使用时需要安装
library("dbCodeBookr")

dt <- read.csv("raw_data.csv")
name_z <- read.csv("raw_codebook.csv")

data <- dt
data[data == ""] <- NA
```

- 正式公开 R 直接使用 `read.csv("raw_data.csv")` 和 `read.csv("raw_codebook.csv")`，不追加 `fileEncoding`、`encoding`、`col.names` 或 `check.names = FALSE`。
- 不用 `names(dt)[1] <- "ID"`、`names(name_z)[1] <- "Easy.label"` 或按列位置重命名修补导出问题。来源别名必须已经按第 1.2 节在下载前确定，并由正式 raw 和 codebook 原样带入。
- 读取区只读取数据、统一空字符串和必要基础类型。`raw_row_count`、完整性断言和覆盖统计放到后台 QA；不使用 `raw_vars <- name_z$newname` 绕行取得数据列。
- 读取区一级标题统一写为 `# ----------- 2 读取数据 -----------`。不在标题后追加“本次 dbCodeBook 导出”“网页导出”或其它来源说明；确有必要时，在标题下用普通注释说明来源。
- 已有全局空字符串处理时，不再默认清理字符串 `"null"`。具体变量需要清理时，依据已经核实的标签就地 `trimws(as.character(...))` 并重编码；必要的实际取值输出只作为依据展示，不承担现场决定口径的任务。

### 2.3 业务区块与读者背景

公开 R 是已经完成事实核对和研究裁决后的解释与实现，不是探索笔记。变量含义、周期来源、编码分组、问法变化、能否合并、缺失与跳题处理在编写公开 R 前就必须确定；仍需靠运行公开代码才能决定口径时，退回数据库探索和候选裁决阶段。

公开代码按“大阶段 → 并列业务模块 → 局部步骤”形成三级层级，不把所有代码块排成同一级。三个层级固定使用阿拉伯数字编号，不使用“一、二、三”等中文序号：

```r
# ----------- 1 定义主题变量 -----------

## 1.1 说明定义框架 ####

### 1.1.1 第一个局部步骤 ####
```

一级标题使用 `# ----------- 1 标题 -----------`，表示来源准备、变量定义、结果检查和正式输出等完整阶段。二级标题使用 `## 1.1 标题 ####`，表示同一阶段内粒度相同、关系并列的业务模块。三级标题使用 `### 1.1.1 标题 ####`，只在一个业务模块确实包含多个可独立命名的局部步骤时使用。不存在的层次不添加空标题，也不为了凑足三级而拆分代码。

读取数据后，第一个主题业务区块为：

```r
# ----------- 3 定义【主题】变量 -----------

# 【用自然语言说明研究内容、定义变量及必要关系。】
```

主题业务代码遵守同一条**读者理解链**，不按探索发生的时间顺序或程序封装顺序复演：

1. **主题总述**：用普通读者能顺畅读懂的自然语言，先说明本次在做什么、为什么需要这样的处理，以及读者接下来会看到什么。背景、来源变化、难点和变量关系只在确实帮助理解时选取，不强制逐项凑齐；具体年份、字段和编码细节留到对应业务小节。
2. **来源事实**：问卷、测验或记录在测量什么，各周期怎样保存，真实标签、编码和结构发生了什么变化。
3. **定义决定**：哪些来源合并或分开，类别怎样归组，跳题、补零、缺失和完整性怎样处理，以及理由是什么。
4. **代码实现**：先让读者看到一个具体来源怎样经过上述规则得到结果，再把已经讲清的同一规则应用到其它周期、槽位或组成项。
5. **结果检查**：定义完成后用必要的 `table()`、`summary()` 检查定义变量范围或分布。

简单变量可以把来源事实、定义决定和代码实现写在同一小节，不为形式完整强行拆标题。复杂变量只看区块标题和相邻注释时，也必须能够复述完整定义链路；辅助函数、依据展示、组成变量、综合得分和结果检查不得排成一串没有业务层次的同级模块。

之后再进入变量字典和正式输出。发生同义周期互补合并且它是当前阶段内的独立业务模块时，可以使用：

```r
## 3.1 合并同义周期来源 ####
```

第一组主题 raw、公式、循环或 helper 出现前，普通读者应当能够用自己的话说出：这段代码准备定义什么、原始数据为什么不能直接拿来用，以及后面的处理大致会怎样进行。为达到这一点需要多少背景、来源变化、难点或变量关系，由主题事实决定，不设固定栏目。

公开 R 的主题总述和笔记摘要共享已经确认的事实，但不互相照搬整段文字。笔记摘要先回答“最终定义了什么、变量怎样组成、问卷原来怎样提问”；公开 R 总述回答“原始记录为什么需要处理、接下来的代码将按什么业务顺序得到这些变量”。摘要不塞入代码路线，公开 R 也不重复目录入口和定义表内容。

主题总述不是摘要表、证据清单或维护者交接记录。优先使用短句和日常表达，一句话只承担一个主要意思；避免连续堆叠“来源结构”“概念边界”“路径”“口径”等抽象名词。必须使用专业概念时，先用普通语言说明它在当前主题中具体指什么。总述过长时，把年份、字段、标签、公式和例外移到它们实际参与判断的小节。

通俗表达不能以删掉关键信息为代价。主题总述中的每句话都应提供能够复述的业务事实，优先说清调查或记录在问什么、哪些人会进入不同提问、这种差异为什么要求后续采用相应处理。不得使用“按真实回答整理”“根据来源处理”“计算相关情况”等没有具体对象、条件和处理方向的空句代替事实；读者读完仍不知道原始记录为什么不能直接使用、后面准备怎样处理时，总述不合格。

主题总述必须区分“原始调查没有收集”与“网站存在来源但本次没有选择、没有下载或下载失败”。前者是可以向读者说明的调查边界；后者是执行阶段的来源缺口，不能写进公开总述冒充数据事实，必须退回候选选择与下载阶段处理。只有完成来源补齐后，才继续编写公开 R 和用户材料。

非综合主题中，来源较多或存在多个并列定义分支时，主题总述按“最终定义 → 各定义分支的来源组成”形成一条连续主线。来源分项数量必须能够与总数对应，并优先按最终定义变量或业务分支组织；不得按内部对象名、字段类型或程序处理顺序平铺技术清单，也不得用两个彼此重启的开场分别介绍定义结果和来源数量。影响实际构造的周期差异放到对应业务小节，影响整个主题解释或比较的周期边界放到小book提示。综合得分、指数或分层定义适用下一条专门顺序。

综合得分、指数或分层定义采用“总述自上而下、定义链自下而上”的结构。公开 R 的主题总述和摘要导读先说明综合定义表示什么、由哪些组成变量形成以及变量之间的关系，再完整说明全部组成变量；最后另起来源层，按组成变量分别说明原始来源数量、问卷结构和周期变化，不把某个组成变量的含义与来源交叉写完后再介绍下一个组成变量。实际定义链仍按“原始来源 → 组成变量 → 综合变量”展开，因此业务代码、`Criteria`、`analysis_vars`、`analysis_db`、`analysis_codebook` 和定义表都先列组成变量、最后列综合变量。综合变量的 `Criteria` 只说明组成关系、公式和完整性，不在各组成项中重复补放综合关系。

问卷把同类信息按人物、机构、项目或其它现实对象反复询问时，总述先说明反复询问的对象，再说明每个对象记录哪些具体信息，最后用“对象数 × 每个对象的信息数 = 原始变量数”解释来源数量。总述只交代理解整体结构所需的组成、产出和边界；编码、路由、公式、冲突与缺失处理放到它们实际参与定义的业务小节。

raw 变量组第一次出现时，就地说明其周期和题目含义。多个变量确实重复同一业务规则时，先用一个代表性来源或一组通俗映射完整展示“原始回答 → 处理规则 → 得到结果”，再定义 helper、循环或矩阵批量复用；不能先摆出抽象工具，再让读者从后续调用反推它解决什么问题。纯输出、排版或 mapping helper 不要求业务示例。

自定义 helper 只能隐藏已经讲清的重复语法，不能隐藏编码含义、类别归组、补零、缺失、阈值或跨周期合并依据。helper 应放在业务规则之后、第一次调用之前，并说明输入代表什么、输出代表什么、为什么值得复用；需要跨多层函数才能理解时，改成按周期、来源或题组展开的直线代码。批量扫描、内部断言和一致性核对放到后台 QA。

数据类型、取值范围、年月配对和特殊编码必须先检查实际 raw，再决定是否处理。只有确认存在字符型数值、无效月份、单边缺失或其它具体问题时，才加入对应转换或清理，并说明依据；实际数据没有该问题时直接使用原值，不为了“保险”机械添加 `suppressWarnings(as.numeric())`、无效值改缺失或其它假设性清理。担心后续数据发生变化时，应使用检查并明确报错，不得用静默改值掩盖变化。

固定检查器、生成器或下游文件明确依赖的函数名、对象名和章节标记属于机器接口，不能为了让文字更自然而自行改名。面向读者的解释应写在相邻标题或注释中；如果固定名称本身不够直观，就用大白话说明它做什么，而不是破坏机器接口。

公开 R 中保留的查看只有两类：

- **依据展示**：在正式构造前，向读者展示已经核实且对理解相邻规则确有帮助的真实标签、编码或结构。注释应先交代已经确认的业务结论以及这段输出用于证明什么，再展示必要结果；不得写成“先看看，再决定如何定义”。连续打印多张只在运行日志中可见、读者必须自行比较才能得到结论的表，不属于有效的依据展示。
- **结果检查**：在变量定义后确认结果范围或分布，可以直接紧跟定义代码，不需要形式化的前后说明。

同一依据展示块中的 `table()`、`unique()`、`summary()` 或 `str()` 必须覆盖紧接着那段判断实际使用的全部原始变量；不能只展示其中几个，随后在 `case_when()` 或公式里无说明地引入其它变量。变量较多时按时期、题组或判断分支拆成多个完整的小块，每块先说清这些变量分别回答什么，再展示和使用。

公开 R 面向第一次接触数据处理的读者。需要展示来源类型、取值、范围、缺失或合并结果时，优先使用读者可以直接看懂的 `str()`、`unique()`、`table()` 和 `summary()`，并在相邻注释中先写明查看目的和已经确认的结论。`stopifnot()`、`identical()` 和批量一致性断言属于后台 QA，不放进公开定义主线代替解释。

用于寻找规律、比较候选方案或决定能否合并的探索代码不进入公开 R；其事实和裁决结论进入“来源事实”和“定义决定”，探索记录保留在数据库流程规定的证据中。批量标签核对、未识别值断言和机器一致性检查进入后台 QA，不用一排 `print(table())` 打断公开定义主线。

### 2.4 注释、封装与代码结构

- 注释解释“为什么这样定义、解决什么数据问题、怎样影响结果”，不逐行翻译语法，也不把已经完成的研究判断伪装成运行时才发现的结论。
- 公开 R 注释面向第一次阅读当前代码的读者，直接说明本段使用哪些信息、为什么这样处理，以及会得到什么结果。版本比较属于独立任务；只有任务本身需要比较版本时，才另设完整的比较说明，不把修改过程混入正常定义步骤。
- 面向读者的注释不直接使用 `helper`、`mapping`、“业务步骤”“技术结果”“处理路径”“双来源”等维护者简称代替解释。需要复用函数时写“辅助函数”，并说明它反复处理哪类具体回答；需要变量关系表时写“变量对照表”；需要分情况处理时直接列出实际条件和结果。术语确实不可避免时，第一次出现必须紧接一句日常语言解释。
- 标题层级对应真实业务粒度。不得增加只负责包住后续内容的空泛标题；同一级应当能直接看出各模块在定义链路中的并列关系。
- 来源分组对象在第一次参与业务处理时就地定义，不为盘点数量而在主题开头集中铺出全部 `*_vars`。被多个并列变量共同使用的来源整理、编码映射或中间结果，放在第一次使用前的共享准备模块，并明确后续由哪些变量复用；不得藏在某一个变量的小节中。仅供 mapping 或正式输出汇总的 `raw_vars` 放到相应输出阶段。
- 公开代码的首要目标，是让具备基础 R 阅读能力的读者理解研究判断。简短、去重和运行效率不能优先于通俗易懂；对少量周期或来源允许重复，封装只在读者先理解具体规则后仍能降低认知负担时保留。
- 除安装包、读取文件、直接赋值等一眼可懂的常用代码外，每个业务代码块前都用简短注释说明“这段代码要解决什么 → 使用什么输入 → 得到什么结果 → 结果接下来用于哪里”。不能因为代码能够运行或对象名看似清楚，就省略读者理解业务目的所需的说明。
- 中间对象第一次出现时说明其内容；条件组合、跨期路由、缺失或补零、公式、汇总、矩阵、循环、`apply` 家族和批量变量必须有就地说明。矩阵、循环或批量变量还要说明每行、每列和每轮分别代表什么；简单常用语法不逐行翻译。
- 复杂过程按实际判断顺序拆分，每一步只完成一种转换，并说明输入、动作、输出和下一步用途。能改成直线代码时不保留多层函数、循环套循环或矩阵套矩阵；确实必须保留时，逐步解释，不能用一段总注释形式完成。
- 公开区创建的普通对象必须有明确用途，并在后续构造、检查、字典或正式输出中实际使用。确认无用途时直接删除，不保留候选对象或用注释为废代码辩护。
- 原始值为“编码 + 标签”时，解码标签用于确认和展示业务含义。少量类别优先用完整标签显式重编码；大量同构变量确需提取编码时，必须先按具体变量和周期说明编码分组，不得把裸数字或全局编码规律当作业务依据。
- 不把工具、路由、后台、旧版本史、验收过程或维护者行话写成用户解释。

## 3. 函数合同

### 3.1 `recode.chr()`

`recode.chr()` 是 RStudio 代码生成辅助，不是运行时清洗函数。

- 适用于真实取值已经核实的简单单变量重编码，例如 `recode.chr(data$raw_var)`；生成后按业务含义修改右侧并固化为逐项 `case_when()`。
- 它依赖已经解码的完整标签生成可审核映射；解码用于确认含义，`recode.chr()` 不负责发现题义、决定归组或判断跨周期能否合并。
- `# recode.chr(data$raw_var)` 必须紧贴同一变量的赋值块；前面可放该变量的 `table()`。
- `table()` 中每个真实原值在相邻重编码块单独占一行，以 `==` 精确匹配。即使多个原值映射到同一结果，也不使用 `%in%` 压缩。
- 单次使用的原值集合不提前抽成 `standard_*` 或 `allowed_*`；稳定且被多个业务判断重复使用时才命名。
- 跨周期合并、多变量计分、汇总、阈值、回溯、正则或其它自定义逻辑不得贴 `recode.chr()` 标签；大量同构字段可在先展示一个具体映射后，用业务清楚的 helper 复用技术动作。
- 不使用 `grepl()`、正则、模糊匹配或泛化 helper 伪装成 `recode.chr()` 生成代码。
- 已核实取值很少的单个分类变量，不使用 `substr()`、`trimws()` 或提取首位编码绕开逐项映射；按上面的 `recode.chr()` 形式把完整原始值逐项写清。只有大量同构变量确需批量处理时，才在展示代表性映射后复用编码提取动作。

```r
table(data$var, useNA = "ifany")

# recode.chr(data$var)
data$var <- case_when(
  data$var == "原始值1" ~ "标准值1",
  data$var == "原始值2" ~ "标准值2",
  TRUE ~ NA_character_
)

table(data$var, useNA = "ifany")
```

### 3.2 `recode.num()`

- `recode.num()` 同样是 RStudio 代码生成辅助，只用于同一变量的真实原值到数值的转换。
- 具体变量注释必须紧贴同一变量赋值；正式 Rscript 不依赖函数运行期返回值。
- 只有 YES/NO 二分类默认使用 `1/0`；其它分类变量默认保留规范英文/ASCII 标签。
- 得分、合计、跨周期统一变量和阈值变量直接实现真实计算，不伪装成 `recode.num()`。

### 3.3 `yyds_coalesce()`

- 来源别名和合并资格必须已经按第 1.2 节在下载前确定。`yyds_coalesce()` 只负责把已经确认属于同一研究概念、编码一致且调查时期互补的来源合并起来，不负责现场判断来源能否合并。
- 列顺序就是合并优先级，调用前必须确认。保留原始列与否由 mapping、来源卡和重叠核对需要决定。
- 调用处只用一句紧邻注释说明合并资格；各来源周期、优先级和特殊值在实际参与定义的位置说明。
- 已经确认可以合并的来源，正式 R 直接调用 `yyds_coalesce()`；不得再按年份手写一组 `case_when()` 重做同一件事。

```r
# 周期互补且含义一致的来源使用同一词干和 _1、_2 后缀
```

### 3.4 `generate_var_details()`

- 周期热图文字始终使用深色。周期不超过 6 个时单行显示；超过 6 个时按原顺序分两行，两行仍溢出才使用横向滑动与箭头。
- 连续变量默认自动选择自然刻度，使柱数约为 12–16 根；横轴显示分组起点，完整区间留在悬停提示中。
- 非负金额正值跨度很大、线性图会挤压主要分布时，直接使用 `hist_mode = "zero_plus_log"`：`0` 单独展示，正值按对数分档。存在负值、`0` 含义特殊或口径不明确时才需裁决。
- 只有正式业务分组宽度已经明确时才设置 `hist_binwidth`；不同变量需要不同宽度时使用命名向量。

## 4. 用户文字共同原则

本节是定义笔记、公开 R 和下游宣传材料共同使用的事实与语言底线，不是要求各载体复制同一段文案。定义笔记、公开 R、公众号 SVG、富文本和其它宣传材料分别按自己的读者任务组织内容；任何载体都不能改变已确认事实，也不能反向产生新的定义规则。

1. **先从已经确认的事实和定义方案生成初稿。**初稿依据实际 raw 取值与标签、正式 codebook、官方材料、已经确认的定义方案和明确裁决。旧 `Criteria`、旧笔记、旧 HTML、历史脚本和既有成品只能在初稿完成后查漏和回归，不作为事实权威或措辞底稿；最终句子可以相同，不为制造差异而改写。
2. **每个事实都有依据。**数字、编码、阈值、权重、区间、来源、周期和优先级不能根据上下文补全。
3. **只写有独立解释价值的信息。**删除后不影响读者理解变量含义、赋值、比较或使用边界的句子不进入用户文本。
4. **忠实于判定口径，不照译代码。**允许调整叙述顺序、合并重复分支、使用公式并直接写转换结果；不复述函数名、中间对象、防御性判断和程序语法。
5. **普通缺失默认省略。**只说明特殊编码、条件性缺失、完整性门槛、部分项目缺失或缺失传播等会改变解释或分析选择的情况。
6. **同一栏目不重复同一事实。**同一事实确实需要跨栏目出现时，每个位置必须承担不同职责和信息粒度，例如摘要只概括来源组成，`Criteria` 再说明具体赋值；不能只是换一种说法重复。
7. **通俗易懂优先于简洁。**先把对象、依据、前后关系和必要例子讲清楚，再删真正重复的文字；不能为了短而省略主语、条件、因果或中间关系。
8. **不使用机械语言指标。**禁词命中、句子重合率、改写率和“旧句复用为零”不能证明语言质量；机器只核对事实、结构和同步。

写入前依次判断：有无正式依据；有无独立解释价值；是否放在正确栏目；普通读者是否无需补背景就能读懂；最后才判断能否更短。

### 4.1 标题、变量名与显示标签

- 笔记标题准确概括本主题实际定义的内容，不能大于分析变量的真实范围。只定义耐用品时不写成“家庭资产”，只定义一种服务时不写成整个上位主题。研究概念在探索后缩窄或拆分时，标题必须在正式生成前同步调整。
- 中文标题优先使用普通读者和相关研究都能理解的概念；英文标题使用含义相同的常见研究表达，不逐字翻译 raw label，也不把处理步骤、数据库模块或内部状态写进标题。
- 标题保留区分研究对象、方向、时间或范围所必需的信息，但不把所有组成变量堆成一串。读者只看标题时，应当能够大致判断本主题定义了什么、没有定义什么。
- 分析变量名和 `analysis_codebook$Label` 是定义结果的统一身份。定义表、`Criteria`、定义卡、图表标题和 defined variable 展示必须与它们语义一致；可以为可读性调整句式，不能改变对象、方向、回顾期、单位或分类含义。
- source variable 的 `Easy.label` 说明原始题目本身，不能因为它最终参与某个分析变量，就改写成分析变量的含义。defined variable 的显示标签来自对应分析变量的 Label。两类标签不得混用。
- 组分概览与组分详情按真实研究概念显式分组，不依赖变量名或 Label 的字符串碰运气匹配。分组名称使用读者能理解的业务概念，不使用内部对象名、循环名或处理阶段名。
- 任何变量重命名或 Label 修改后，必须一次核对并同步：`analysis_vars`、`analysis_db`、`analysis_codebook`、mapping、定义表、全部 `Criteria`、Easy.label、组分概览与详情、定义卡、图表标题，以及公开 R 中对应的章节标题和注释。发现旧名残留或含义错配时不得发布。
- 全文审核必须把所有读者可见的标签和图表文字当作正文阅读，包括 source variable 的 Easy.label、analysis variable 的 Label、组分详情、定义卡、坐标轴和图例。变量代码名保持原样；解释性文字若仍是维护者英文、内部缩写或读者无法直接理解的短句，应改成说明对象、题义或结果的自然语言。

### 4.2 通俗表达的具体标准

笔记面向没有数据库、R 语言或问卷设计背景的普通读者。所谓“通俗易懂”不是删掉事实，而是把事实按照日常理解顺序说完整。每段先回答一个具体问题，例如“调查问了谁”“问了什么”“为什么不能直接合并”“最后怎样处理”，不能只堆抽象结论。

- 使用完整、自然的主谓句，明确谁做了什么、在什么条件下得到什么结果。避免省略主语后连续堆放“来源、口径、路径、边界、结构、身份、机制”等抽象名词。
- 优先使用读者熟悉的现实对象，如“受访者”“配偶”“子女”“家庭”“医疗机构”和“过去一年”。专业词确实必要时，第一次出现立即用日常语言解释，后面才可简称。
- 内部技术词不能直接充当解释。需要表达时，改成读者可以观察或使用的事实：
  - “数据层级”说明为“一行代表一个人、一个家庭，还是一名家庭成员”；
  - “回顾期”说明为“调查询问的时间范围，例如过去一个月或过去一年”；
  - “结构性缺失”说明为“受访者因前面回答而跳过这道题，并不是漏答”；
  - “来源身份变化”直接说明“谁回答、问的是什么或来自哪类问卷发生了变化”；
  - “周期边界”直接说明“哪些年份可以比较、哪些年份含义不同，以及为什么”。
- 先说业务事实，再给变量名、编码或公式。不能用一串 raw 名、裸编码或函数名开场，让读者自行推断题义。
- 一句话只承担一个主要意思。需要同时说明对象、年份变化、数量和处理结果时，拆成短句、分行或简表；不能把所有限定条件塞进一个长句。
- 只有抽象规则仍难理解时，补一个真实且必要的例子。例子用于解释规则，不重复制造另一套定义，也不能用例子替代完整规则。
- 通俗表达不能变成空话。“根据实际情况处理”“按相应规则计算”“不同年份有所变化”等句子如果没有说明具体对象、变化和处理方向，必须重写。
- 每段写完后做一次零背景复述：不看代码和上下文，普通读者能否说出这段在讲谁、发生了什么、为什么重要、最终怎样处理。不能复述时，说明对象、条件或因果仍然缺失。

### 4.3 特殊情形触发表

只在真实命中时应用，不为填满模板制造内容：

| 情形 | 必须核查 | 读者最终需要理解什么 |
| --- | --- | --- |
| 大量循环变量 | 对象、类型、方向、周期等真实维度，各组列数与总数 | 读者能看懂问卷对哪些现实对象反复提问、每次记录什么，以及为什么会形成许多原始变量。只有乘法确实帮助理解且问卷结构已经核实时才展示数量，不从变量后缀推测人数限制 |
| 跨周期问法变化 | 共同研究含义、回顾期、题目形式、记录方式、采用信息 | 读者能分清哪些内容各期相同、哪些内容发生变化，以及这些变化为什么影响定义或比较。是否使用背景段、列表或表格由内容决定，不规定固定开场 |
| 直接回答与推导混用 | 哪些周期直接回答，哪些周期由金额、次数或分项推导 | 先区分记录方式，再明确各自判定条件；不得用“直接记录”等模糊表述跳过中间逻辑 |
| 多来源优先或回填 | 主来源、补充来源、触发条件和顺序 | 读者能知道什么情况下使用哪个来源，以及后一个来源何时才会参与 |
| 跳题或筛选题 | 上游筛选、进入条件、下游空白含义、适用对象 | 明确 No 或结构性跳题何时应为 0，Yes 后信息不足何时缺失；无法区分时不擅自补 0。参与判断的筛选信息必须进入 raw、mapping 和公开代码 |
| 公式变量 | 最终公式、输入、换算、权重、完整性 | 读者能复算结果，并知道输入不足时怎样处理 |
| 汇总变量 | 构成最终结果所需的全部组成项 | 读者能看懂由哪些组成项得到结果、何时可以计算，以及组成项不足时怎样处理 |
| 不同原始题目导致最终变量冲突 | 各变量的直接来源、冲突方向、数量和是否有用户裁决 | 默认按直接来源分别生成并保留冲突，不为内部一致性改值；`定义逻辑` 写各自生成规则，只影响单个变量时由该变量的 `注意点` 说明冲突题目、数量、表现和解释影响，同时影响多个变量或整个主题时再由小book提示说明总体边界。只有用户明确要求时才写修正规则 |
| 周期缺少对应来源 | 缺少的题目或来源、实际赋值、解释边界 | 按“缺少什么 → 怎样赋值 → 能表示什么、不能表示什么”说明 |
| 来源身份或题义变化 | 实际语义、对象、项目结构与可比性 | 只影响单个变量的判定或解释时进入该变量的 `定义逻辑` 或 `注意点`；同时影响多个变量或整个主题的周期比较时进入小book提示。题义不变、仅 raw 名变化时在 `定义逻辑` 交代必要来源，不另写注意点 |

## 5. `Criteria`

### 5.1 栏目职责

- `定义`：用一句完整的话回答变量表示什么。优先写清研究对象、测量内容，以及属于变量含义的回顾期或单位；不写调查年份、raw 名、来源文件、处理过程、缺失或研究建议。
- `定义逻辑`：写真正影响结果的适用对象、判断来源、赋值、计算、优先级、补零、特殊缺失和完整性，按实际决策顺序组织。
- `分类`：只列最终编码和类别含义；连续变量默认只写“连续变量”和单位。理论最大值、观察范围和极端值进入 QA，除非范围本身属于正式定义。
- `注意点`：只写当前变量不属于赋值步骤、但影响追溯、比较或解释的事实。影响多个变量或整个主题的来源与周期边界、数据层级和重大结构问题放到小book提示，不在每个变量中重复。没有内容时省略整个栏目，不写“无”“暂无”或“不适用”。

### 5.2 写作规则

先在 `文案.md` 的 `## Criteria` 下，按最终定义变量逐项写完整。文案中只写读者会看到的文字，不写 HTML、样式或渲染函数。每个变量核对通过后，再把原文放进 `definition_data$Criteria`；进入生成源时不得顺手压缩、改写或补句子。

- 普通单题直接写“题义 + 回答选项 + 赋值”。题义和判定不变、只是跨周期更换 raw 名时，统一赋值只写一次，周期与必要来源放在同一编号项。
- 同一对象、含义和回顾期跨周期保持不变时先交代共同口径，只展开真正变化的部分；判定相同的周期合并书写，不按年份机械排比。
- 多步骤定义按“适用对象 → 判定来源 → 赋值或公式 → 补零与特殊缺失 → 完整性”的实际决策顺序组织。主题事实不需要其中某一步时直接省略，不为凑齐模板制造内容。
- 下游变量只对已经定义的上游变量重新归类时，只说明分组关系，不重复上游清洗。
- 原始选项保留问卷或 raw 的真实标签；基于题目前提、结构或裁决推定的换算值在 `注意点` 说明依据和解释边界，不改写成原始选项。
- 正常数值按题目单位保留时，不写“其余非负数保留原值”等防御性条件。
- 不把 `TRUE ~ NA`、未匹配类别或程序兜底翻译成用户说明。真实存在的拒答、不知道、不适用等特殊值按其实际含义说明。
- 跳题或筛选题参与定义时，明确区分：已经确认没有发生时何时记为 0；应当继续回答但信息不足时何时保留缺失；无法区分正常跳题和漏答时不得擅自补 0。
- 公式变量按“最终公式 → 各项输入 → 单位或时间换算 → 完整性与缺失传播”说明；不能只给计算结果而省略输入条件。
- raw 名只在追溯或区分来源确有必要时放在对应业务句中或句末，不能先堆 raw 名再让读者反推题义。
- 多项规则使用 `① ② ③...`。只有当前变量后续多条判定共同依赖一个必要前提时，才在编号规则前使用公共 `criteria_context()` 渲染浅底背景块；适合放入的内容限于跨期组成变化、适用人群或容易误解的解释边界。普通变量含义、简单组成清单、具体赋值、公式、补零和缺失处理仍写在正常定义逻辑中，不使用底色强调。没有独立前提时省略背景块，不为统一外观机械添加。背景块直接讲清事实，不加“各年的来源不同”等固定开场。`分类` 使用短横线；小标题单独一行并加粗，内容保持轻量缩进。
- 变量名和代码对象使用 inline code；数据取值、编码、分类值和问卷选项使用方括号强调，不写成 inline code。
- 审核通过后的 `definition_data$Criteria` 是唯一生成源。definition HTML、笔记和其它用户材料从这里生成，不手工各改一版。

原始矛盾专项只在用户明确要求时执行，不作为每个主题的机械扫描；但在正常定义或验证中已经发现的矛盾不得忽略。发现后按以下默认规则处理：

1. 各定义变量按自己的直接原始题目分别生成，不替受访者判断哪道题正确。
2. 允许状态、金额、次数或其它分别来源的定义变量互相矛盾。例如筛选题为 No、金额题为正金额时，状态保留 0，金额保留正金额。
3. 未经用户明确裁决，不得采用筛选题优先、金额题优先、强制补 0、改缺失、删除金额、排除记录或其它内部协调规则。
4. 在过程证据中保存冲突记录，至少包含身份键、周期、涉及的原始题目与原回答、冲突方向；生成规则写入相关变量的 `定义逻辑`。只影响单个变量时，由该变量的 `注意点` 说明题目、数量、表现和解释影响；同时影响多个变量或整个主题时，再由小book提示说明总体边界。
5. 能按直接来源分别忠实生成时，报告后继续，不自动进入 `RESULT_REVIEW_REQUIRED`。只有单个定义变量自身的来源或生成规则无法确定，或存在来源不明、重复计入、多来源覆盖规则不明等实质问题时才暂停裁决。

触发专项后还要说明来源组和最终是否保留或按用户裁决修正，不把派生关系或正式覆盖误写成原始冲突。

`Criteria` 的 HTML 结构、颜色、缩进和间距由公共 helper 与固定测试维护；主题脚本只提供语义内容和结构标记，不复制 CSS 实现。

## 6. 摘要导读与小book提示

固定顺序为：**最终定义信息区 → 可选关系结构 → 原始问卷与时期分组 → 可选小book提示 → dbCodeBook 目录入口**。摘要先让读者知道最终得到什么，再按真实时期说明问卷原来怎样提问以及设计发生了什么变化。目录入口只在上述内容之后简要交代。来源与周期边界、数据层级与分析单位，以及跨变量或整个主题的重大结构问题由小book提示承担，不在首段或目录入口重复展开。摘要不再生成五列表；全部分析变量及其顺序由后面的 `Definition / Criteria / detail` 定义表展示。

摘要导读、小book提示和参考资料说明先写在 `文案.md`，读顺以后再放进主题生成源。公开 R 不走这一步，按第 2 节结合代码编写。

加入样式前，逐段做一次零背景检查：

- 假定读者不了解数据库、问卷和 R。
- 读者应能说出最终定义了什么、各部分是什么关系、为什么需要这些原始变量，以及每段话为什么出现在这里。
- 遇到内部术语、突然出现的数字、前后跳跃、空话套话，或虽然简短但不能复述的句子，先改清楚。
- 没有读顺以前，不加颜色、链接、卡片或其它样式，也不运行正式渲染。
- 审核记录要写明实际发现和修改，不能只写“已通读”或 `PASS`。

文字通过以后，样式阶段只能添加语义标记，不能改句子。确实需要改字时，先回到 `文案.md` 修改并重新通读。渲染完成后，再提取摘要导读、小book、全部 `Criteria` 和参考资料的可见文字，与 `文案.md` 逐段核对；文字不同就不能发布。

### 6.1 先说明最终定义了什么

- 摘要开头先让读者知道最终定义了哪些变量、各变量表示什么，以及它们之间有什么关系。
- 摘要首段中的定义变量总数、定义结果名称和关键概念使用既有语义标记显示主题色。成组列出多个已经命名的定义结果时，每个名称分别保留中文引号并单独标记，例如“总费用”、“自付费用”和“自付比例”；多组变量共享“是否发生”“金额”“比例”等最终结果维度时，这些维度也要分别标记，不能只突出组名。主题色只作用于引号内文字，标点、连接词和解释句保持普通文字颜色。不得只高亮总数或组名，却把读者真正需要识别的结果名称埋在普通正文里；也不得把整句话全部染色。同一概念在同一自然段或同一个连续信息块中原则上只标记一次；后文继续解释时改用“这一组”“最后一项”等自然指代，或保留普通文字，不重复着色制造两个视觉重点。
- 只有一个定义变量时直接点名，不使用“等”；多个变量时完整列出，或在不遗漏关键分支的前提下概括后明确总数。
- 综合得分、指数或分层定义先说明综合定义，再完整说明全部组成变量及其关系。非综合主题先说明全部定义变量或真实业务分支。
- 开头不介绍目录、检索过程、逐年 raw、赋值细节、特殊编码、周期可比性、数据层级或重大结构问题。

### 6.2 再说明调查原来怎样提问

- 这一部分解释为什么需要这些原始变量：调查问了谁、问了什么、怎样反复记录，以及这些信息分别用于哪些定义变量。原始变量总数只需在能够准确核对时说明一次，不围绕计数组织整段文字。
- 面向读者的笔记、`Criteria` 和公开 R 统一使用“原始变量”。不得用“来源字段”“raw 字段”“来源项”等内部说法代替。只有确实讨论数据表中的列结构时才使用“字段”，并立即说明该字段具体记录什么。
- 来源简单时用自然段；内容复杂时可以按现实对象、业务分支或问卷阶段分组。选择哪种结构只看哪一种最容易让读者理解，不预设固定标签、固定段数或固定句式。
- 涉及多版问卷时，各时期分别讲清当时真实的询问对象、问题内容、继续追问的信息、跳题程序和记录方式。某一期特有的问法必须留在该期，不得写成所有年份的共同规则。
- 官方问卷能够核到原题时，直接呈现所有实际参与定义的题目，不再只挑一两个问题概括问卷流程。每道题按原问卷保留题号、中文原题、回答选项、填答单位和影响定义的跳题说明；访员提示、卡片内容或无关支路只有确实影响题义或取值时才保留。摘要的问卷结构区使用统一题块：分组标题、题号和问题顶格，题号加粗，中文原题不加引号；回答选项及跳题说明逐行缩进。回答选项独立设置为 `0.8em` 和 `#888888`；题干后的进入条件与选项后的跳题说明都独立设置为 `0.72em` 并继承正文默认深色。字号不得通过父子元素的 `em` 相乘得到。同一行同时包含回答选项与跳转信息时，两者使用同级、互不继承字号的文本元素。题号、题干、填写说明和访员说明不设置文字颜色。主题内影响定义的跳题按原问卷保留；主题出口的读者表述按下方模板处理；“填写”“记录”等提示只有原问卷确实出现时才加入选项。整个时期标签内容统一使用正文的 `0.92em`；时期内第一个分组标题不增加上方间距，后续题组标题和相邻问题之间保留轻量间距。根据变量标签或数据结构推断的题意只能写成概括，不能放进原题题块。
- 如果一个主题涉及的研究问题、问卷分支或原题数量过多，已经无法在时期标签中完整、自然地讲清楚，应在撰写 `文案.md` 之前按独立的研究问题拆成多个主题。拆分以“每个主题能够完整说明一组定义变量及其全部必要来源”为准，不设置机械的变量数或原题数门槛；不得拆散同一个定义变量，也不得把同一条定义链路分到不同主题。共同筛选题可以在相关主题中重复说明，但不能因为别处出现过就省略本主题理解定义所必需的题目。禁止用删减原题、只列题号范围、把不同对象或业务支路合成一句概括等办法控制篇幅。
- 多道原题的回答选项和跳题条件完全相同时，每道题的题号和题干仍要完整列出，但相同选项可以在这一组题目之后集中列一次，并明确哪些题共同使用；存在不同选项、不同单位或不同跳题路径的题目，差异必须紧跟对应原题，不能被合并说明掩盖。
- 原始问卷按下面的展示模板排版。方括号为占位内容；题干、选项、进入条件和跳题方向均以本期原问卷为准。需要交代进入条件时，必须写明原问卷据以判断的题号及回答，或问卷明确生成的程序变量；入口由多题共同决定时如实列出这些题。判定题未在当前题组展开时，同时简述该题识别的工作或对象，不能只列题号，也不能改写成无法追溯的对象概括。进入条件紧跟题干放在同一行的全角括号内；没有特别条件就省略，不显示“题前说明”标签。访员提示、占位符解释和来源标注不写成进入条件。

```text
**FA001** [完整原始题干]（[符合原问卷进入条件的受访者回答本题]）
  1 是 → 结束该主题
  2 否
```

本分支不再进入本主题问题时，选项后统一写 `→ 结束该主题`，不附原问卷出口题号或题目解释。主题内的条件跳转保留 `→ 跳至 [准确题号]`；普通顺序作答不逐个选项补写“继续下一题”。是否结束本主题按完整问卷路径核对，不能把暂时经过无关题目后仍返回本主题的路径写成结束；不另设“题后说明”。

笔记正文不标注“（官方流程图）”，也不集中声明跳转依据来自官方流程图。实际题号、完整路径及官方材料依据保留在内部来源证据中，用于核对，不搬入读者文案。影响题义且必须保留的访员提示或占位符解释放在该期“问卷设计”说明中，不与答题对象混写。

- 每个时期的说明都先客观交代本期询问哪些对象和信息、问题怎样继续追问，让读者不依赖前一个标签也能理解本期问卷；再另起一段说明它相较前一时期新增、取消或改变了什么。例外应先直接说明具体缺少或不同的题目，再解释其它问题怎样继续，避免用“除……外”把关键事实藏在从句里。第一个时期作为比较起点，应把完整提问程序讲清楚；后续时期不必重复抄写所有未改变的原题，但不能直接从“与上一期相比”开头而省略本期实际问了什么。说明标题统一使用“问卷设计”。“问卷设计”块的首段顶格，第二段及以后首行缩进；缩进由公共渲染组件统一生成，不在主题文案中手写空格。
- “问卷设计”或“问卷设计变化”的说明文字保持自然叙述，并用中文引号标出这一部分实际询问的核心问题或信息。引号内可以是简短的问题概括或信息名称，不要求照抄完整原题，也不必改写成带问号的新问句；但不能改变询问对象、时间范围、支持方向、条件和含义，也不得称为“原题”。下方按题号、题干、选项展开的结构化原始问卷题块才负责呈现核对过的原题，并且仍不加引号。一个时期同时涉及多个相对独立的对象或问题组时，可以用①②③直接标出各部分；信息较多时可以分成多个自然段。编号和分段只用于帮助读者看清内容关系，不得机械地给每句话编号，也不得把本来连续的一件事拆碎。
- 原始问卷与项目处理必须分开。时期标签只按“原始问卷题目与选项 → 原问卷跳题路径 → 发布数据怎样保存 → 问卷设计发生的变化”说明调查事实，不设置“定义处理”栏目，也不写项目的逐变量赋值。如何记为 0、1、金额或缺失，怎样计算、补零和处理例外，统一写入对应变量的 `Criteria`；不能把项目结果倒写成问卷提问方式，也不能在原题中间穿插代码判断。
- 问卷按人物、机构或项目反复提问时，说明现实中的提问过程和每次记录的信息。不能仅根据变量后缀或宽表列数推断“最多 N 人”“前 N 人”或固定顺序。原始变量数量或乘法只有在准确且确实帮助理解时才展示。
- 跨周期总数从最终采用的原始变量按完整来源身份去重得到。不同问卷版本的数量只有确认互不重叠时才能相加；否则只报告去重后的总数，不展示误导性的算式。
- 中文引号只用于正文中直接引用的问卷原题或访员说明、原始回答选项，以及确实需要与日常含义区分的概念。摘要的结构化问卷题块不加引号，使用 `summary_questionnaire_line()` 生成。问卷分组标题使用主题色加粗；回答选项使用 `0.8em` 和 `#888888`；题干后的进入条件与跳题说明均使用独立的 `0.72em` 并继承正文颜色；题号、题干、填写说明和访员说明均继承正文默认颜色。
- 来源组成、原始题目结构及其与定义变量的对应关系以完整、清楚为优先，不得为了缩短摘要而删除理解或复核所需的信息。内容较长时，将这一完整信息区标记为 `.raw-source-structure`；网站前端可以据此提供展开或收起，但笔记源文件、复制内容和导出材料必须保留全部正文。折叠属于展示层处理，不能反过来要求定义文案缩写。
- 多个年份或问卷阶段需要分别完整说明时，在 `.raw-source-structure` 内按真实年份或阶段建立 `.raw-source-period` 分组，并用 `data-label` 保存读者可见名称。笔记只负责完整内容和语义分组，不写标签按钮、隐藏样式或切换脚本；网站可以将这些分组显示为标签页。没有网站脚本、复制全文、导出或打印时，所有分组必须仍然完整存在。

#### 6.2.1 调查时期分组的笔记生成规则

调查时期分组用于按年份、Wave、调查阶段或问卷版本分别保存完整说明，CHARLS、ELSA 及其它数据库共用同一套笔记结构。

1. 主题生成源使用 `.raw-source-structure` 包住整个来源说明，按真实调查顺序为每个时期建立 `.raw-source-period`，并用 `data-label` 保存该时期的读者可见名称。
2. `.raw-source-period-label` 只保存无脚本环境需要显示的时期名称，必须使用普通文本容器，不得使用 Markdown 标题或 `h1` 至 `h6`。
3. 每个时期的正文必须完整保留在对应分组中。主题脚本不得生成标签按钮、展开收起逻辑、内容高度、边框、间距或其它网站样式。
4. 没有网站脚本、打印、复制全文或导出时，所有时期正文和时期名称仍须完整显示，不能因网站采用标签页而丢失内容。

网站识别上述语义结构后，由公共前端自动完成标签显示和交互；主题生成源不得重复实现网站渲染逻辑。

- “摘要导读”只有整节最开头的总述首段顶格；后续自然段由网站统一设置缩进。笔记正文不手写空格或 HTML 空格模拟缩进。
- 来源组成之后，用一句单独成行的简短文字说明可从 dbCodeBook 的哪个真实完整目录进入。多个来源共享父目录时优先展示一次稳定父目录；来源分散时展示最能说明主题的入口，并中性说明还有其它来源。目录记录数只有帮助理解且能对应紧邻展示的同一实际目录时才保留。
- 普通检索关键词、翻页、排除候选和其它探索过程不进入摘要。真实发现路径、页面观察和判断过程同步保留在数据库流程规定的 `探索记录.md`；`definition_search_record.json` 只保存与同号步骤对应的机器对账信息。
- 摘要和时期标签不展开逐变量赋值、特殊编码、公式、补零、缺失、QA、下载、验收和制作过程，也不另设“定义处理”块。影响单个变量的判定写入 `Criteria`；影响多个变量或整个主题使用的边界写入小book提示。

### 6.3 定义表、关系结构与文献

- `Definition / Criteria / detail` 定义表必须覆盖 `analysis_codebook` 中的全部分析变量，并与 `analysis_vars`、`analysis_db` 和 `analysis_codebook` 保持相同顺序。综合得分、指数或分层定义统一按“组成变量在前、综合变量在后”的定义逻辑排列。
- 定义表、定义卡、图表和 detail 不要求逐字使用同一句话，但必须表达同一个对象、方向、回顾期、单位和分类。变量重命名后按第 4.1 节执行整套同步核对。

- 只有定义变量存在已确认的多层组成关系时，才在最终定义信息区之后增加等宽代码树；普通单层主题省略。
- 代码树只使用正式节点名称、范围和已确认公式，不新增阶段标题或解释。前导空格和树线属于结构，必须保留。
- 文献只收录直接支持公式、计分、阈值、构造方法或解释边界的原始方法、正式指南、官方技术材料或不可替代的高质量研究。只说明“有人这样用过”的普通应用论文留在过程证据。
- 官方问卷用于核对原题、选项、回顾期、询问对象和跳题程序。上述内容已经在“原始问卷与时期分组”中直接展示时，不再把同一份问卷列入文献区重复说明；某期没有继续收集某类问题，也在对应时期标签或必要的小book提示中讲清楚，不另列一条问卷引用。
- 官方材料只有在问卷题目之外还明确规定了派生变量、公式、阈值、计分或方法边界时，才作为方法依据进入文献区，并且只说明它额外支持的那部分。原题展示不能代替方法文献，方法文献也不能代替原始问卷事实。
- 笔记引用只能来自候选阶段已经同步记录的官方材料或文献核对；不能在笔记完成后为了装饰或补格式临时寻找引用。正文实际采用而探索记录未登记的证据，必须先回到探索记录补做真实核对，不能根据成品反向编造调研过程。
- 每条引用用大白话依次说明：这份材料研究或规定了什么 → 它具体支持本主题的哪一部分 → 哪些来源连接、跨期处理、缺失处理或公式仍是本项目自己的决定。材料没有报告的内容直接说明“该材料没有说明”，不得写成含糊的“提供参考”。
- 引用放在完整定义表格之后、`## 材料`之前；与表格空一行，多条之间不留空行。每条使用 `> 1、文献内容`，标题链接到正式来源。

### 6.4 小book提示

- 小book提示只说明同时影响多个定义变量或整个主题理解与使用的宏观边界。只有命中以下至少一类且值得普通读者了解时才生成；没有则省略整张卡：
  1. **来源与周期边界**：不同周期的询问对象、回顾期、问卷范围或来源身份发生整体变化，影响跨期比较或解释。
  2. **数据层级与分析单位**：家庭、个人、家庭成员、社区或其它层级之间的对应关系会影响样本量、重复记录、汇总或研究单位。
  3. **跨变量或整个主题的重大结构问题**：同一问卷结构、样本覆盖、原始矛盾或其它事实同时影响多个变量，不能靠阅读单个变量的 `Criteria` 完整理解。
- 同一张卡按实际复杂点使用 `① ② ③...` 和普通换行；只有一点时不强制编号。
- 面向普通读者时通常控制在 2 至 4 个短段落，每段只承担一个主题级边界。超过这一范围时，先把重复的时期说明、单变量处理和 QA 计数移回时期标签、对应 `Criteria` 或过程报告；只有这些信息确实共同改变整个主题的理解与使用时才继续保留。
- 小book标题后的第一段不缩进；连续叙述从第二段开始首行缩进 `2em`。以 `① ② ③...` 或数字序号开头的分项本身不缩进。段落结构和缩进由公共生成工具统一写入笔记，不由网站补做，也不在 `文案.md` 中手写空格。
- 每点直接说明“需要注意什么 → 真实例子 → 为什么影响本次定义”，按需补充已经确认的处理结果。不要用“上一波次预载信息：”“跨年份变量演变：”等类别标签机械开头。
- 提示卡直接写读者需要理解的调查对象、记录范围和使用影响。上游主题或变量只有在确实参与当前主题的适用对象判断、结果保留或解释边界时才写入，并当场说明它在当前主题中起什么作用；与结果解释无关的主题编号、核对数量和跨主题一致性检查留在过程证据。
- 同一主题级边界只设一个主要说明位置。已经在小book提示中完整说明的空白含义、适用对象或跨期比较边界，摘要导读和来源入口不再重复；摘要只介绍定义结果与关系，来源入口只说明去哪里查看原始来源。
- 整张卡必须形成一条能连续读懂的说明链：先交代主题级边界或结构事实，再用真实周期、对象、记录方式或数据层级说明具体表现，最后说明它怎样影响比较、汇总或解释；只有本次确实作出处理时才补充处理结果。编号用于分开不同复杂点，不把因果相连的事实硬拆成互不衔接的孤立条目，也不为追求条数而机械合并。
- 只影响单个变量的特殊编码、补零、缺失、异常、冲突或适用条件放在该变量的 `Criteria`；不得为了填充提示卡重复搬运。一个问题即使同时影响同一业务分支中的多个状态或金额变量，只要没有跨越不同定义分支、也不改变整个主题的比较或使用方式，仍优先在这一组变量的 `Criteria` 中说明，不能仅凭“影响多个变量”放进小book。问卷按现实对象重复展开但只用于解释来源数量时，留在摘要的来源组成；只有这种结构进一步影响多个定义分支或整个主题的解释与使用时，才进入小book提示。
- 生成提示卡前，逐句与时期说明和全部 `Criteria` 对照。如果提示中的事实已在这些位置完整讲清，而且没有新增主题级解释边界，就在 `文案.md` 写明“本主题没有需要单独提示的主题级边界”，正式笔记省略整张卡。不得仅为保留版式而把已有内容重新汇总一遍。
- 变量名和代码身份在生成源中使用成对反引号，由公共 helper 转为 inline code；主题脚本不手写 `<code>`。
- 提示卡不是 `Criteria` 的压缩版，不展开完整赋值流程，也不添加难易评价。

### 6.5 语义标记与载体

- 问卷题块沿用 `summary_questionnaire_line()` 生成；展示以第 6.2 节模板为准。既有调用保持兼容，不因本次展示调整要求历史主题改写生成代码。
- `文案.md` 直接写完整题干、选项、进入条件和逐项跳转，最终笔记保留相同的文字与顺序。进入条件紧跟题干并用全角括号包住；最终题块将进入条件与跳题说明显示为同一档正文深色小字，选项显示为稍大的浅灰文字。三者各自设置字号，不使用嵌套字号。排版在已有全文审核中对照模板检查，不要求额外的位置标记或专用检查报告。
- `dbCodeBook` 保持正文样式；完整目录标记为目录；数量只标记数字；需要与日常含义区分的定义概念保留中文引号并只标记引号内文字；变量名使用 inline code。“问卷设计”或“问卷设计变化”说明中的引号内文字使用 `.summary-period-question` 与 `data-summary-period-question="true"` 标记，并显示主题色；引号和说明中的其它文字保持正文颜色。核对过的问卷原题使用 `.summary-question` 与 `data-summary-question="true"` 单独标记；题干后的进入条件使用 `.summary-question-condition[data-summary-question-condition="true"]`，或结构化题块中的 `[data-summary-question-detail-role="instruction"][data-summary-question-position="before"]` 标记，独立设置 `font-size:0.72em` 并继承正文颜色；结构化题块另用 `.summary-questionnaire-line` 标记并缩小一号。回答选项用 `data-summary-question-option="true"` 或 `data-summary-question-detail-role="option"` 标记，独立设置 `font-size:0.8em;color:#888888`；选项后的跳题说明用 `data-summary-question-instruction="true"` 标记，独立设置 `font-size:0.72em` 并继承正文颜色。承载同一选项和跳题说明的外层只负责换行与缩进，不设置字号。位于选项后方的其它填写说明和访员说明不设置颜色。问卷分组标题使用主题色，整段解释不额外着色。
- 中文数字与量词之间留一个半角空格，例如 `12 个`、`2020 年`；百分号紧贴数字。数字与量词使用不可断开的语义容器。
- 同一概念只强调首次出现，后续保持正文样式。
- 笔记、公众号 SVG、富文本和其它载体共享同一事实与语言底线，但不共用整段成品文案。宣传材料面向普通读者，根据正式定义事实重新组织内容，不能直接搬运笔记段落，也不能为了版式改写变量含义、数字、公式或边界。颜色、圆角、间距和卡片布局由各载体公共模板维护，不反向写成第二套定义规则。

## 7. 其它用户材料与同步

- `### 1-提取变量` 必须包含非空的 `bookapp显示名=变量名` 列表和一个 `Go to 提取变量` 按钮；不得保留占位文案。
- detail/组分概览按真实研究概念分组，每组先显示 `source variables`，再显示 `defined variables`。分组名称使用普通读者能理解的业务概念；source variable 的 Easy.label 说明原题，defined variable 的显示标签说明分析变量。正式 R 显式设置 factor levels；未匹配变量进入 `Other / check` 并触发 warning 或 QA。
- detail 片段自行提供 `## 定义的组分概览` 和 `## 定义的组分详情`；笔记拼装器不得再额外添加“定义的组分详情”。最终笔记各保留一个标题，不能形成“详情 → 概览 → 详情”的重复结构。
- 用户材料只解释数据对象、变量语义、周期逻辑、必要来源差异和研究使用影响；工具、版本史、验收状态和过程证据留在机器报告或内部证据。
- 定义笔记摘要负责“定义结果、变量关系、来源组成和目录入口”；`Criteria` 负责逐变量判定；小book提示负责主题级边界；公开 R 负责解释并实现定义过程；宣传材料负责把已确认事实重新组织成适合相应平台阅读的内容。
- 摘要、`Criteria`、detail 分组和公开 R 分别从各自正式生成源同步。正式定义事实变化后，再由独立的宣传任务评估并刷新需要更新的宣传材料；宣传材料不作为定义笔记或正式 R 的措辞底稿。

### 7.1 全文文案门

完整笔记生成并通过事实与结构检查后、同步网站前，必须依次完成作者全文检查和普通读者检查。作者先从头到尾阅读最终版整篇笔记和公开 R；普通读者随后只阅读最终笔记的可见文字，不先看 R、数据、探索记录或作者解释。两次检查都不能用旧版审核、分别看过各个局部、机器格式检查或一句自报 `PASS` 代替。

作者全文检查只是把各部分放回整篇笔记后再读一遍，不改变前面的写法：摘要、小book、`Criteria` 和参考资料对照纯文字稿检查；公开 R 连同相邻代码一起检查。公开 R 不能因为也要参加全文审核，就脱离代码提前写注释。

当 `public_r` 发生变化时，`public_r_comments` 审核不能只评价注释。必须把公开 R 按实际定义步骤分成若干完整代码块，并在 `code_walkthrough` 中逐块记录：这段读入什么、执行什么判断或计算、得到什么、用日常语言怎样复述。只有审阅者不依赖作者口头补充就能顺着实际表达式讲清整条定义链，才能通过；如果解释必须跨越多层辅助函数、循环、正则或隐含编码，先把代码改成读者可以沿顺序阅读的写法。检查器在 `public_r` 变化时强制要求这份逐块记录，只有“注释清楚”或一句总评不能生成发布许可。

两次检查都只处理读者表达，不自行扩大为来源重查、环境修复、变量重定义或宣传制作。普通读者发现事实本身不确定时，只记录疑问并退回作者，不自行打开技术材料寻找答案；作者再回到事实确认阶段处理，不能用润色掩盖问题。

作者先完整读一遍成品，了解整篇文章的结构，再集中修改已经发现的问题。下面八项只是防止漏看内容的覆盖清单，不是写作模板，也不规定必须按八项顺序写文章。修改后重新生成，并再次从头读到尾；不能一边发现一句、一边反复生成。

审阅必须覆盖八项：

1. `title_summary`：标题、摘要导读与全文开场；
2. `definition_logic`：定义关系、共同背景、问卷变化与逐项判定；
3. `criteria`：全部变量的 `Criteria`，包括跳题、补零、缺失、完整性，以及已发现的原始题目间矛盾是否按直接来源分别保留并具体披露；
4. `insight_card`：小book提示实际表达了什么，不只检查卡片格式；
5. `references`：文献逐条实际支持什么，不把本项目 raw、跨期、缺失或公式说成文献结论；同时检查是否把时期标签已经展示的官方问卷再次列入文献区，或把没有额外方法作用的材料仅为凑数保留；
6. `public_r_comments`：公开 R 的大框架、局部说明和零基础读者理解链；
7. `labels_charts`：定义表、标签、Easy.label、mapping、codebook、定义卡与图表文字；
8. `full_note_flow`：按最终顺序从标题到文献引用完整通读后的段落衔接。不能只写“已完整通读”或“前后一致”；必须记录各主要段落承担的作用，并检查相邻段落之间的对象、业务分支、时间阶段和定义层级是否连续。出现切换时，应引用前后实际文字并说明过渡是否充分。

通过标准不是禁词、句长或改写率，而是没有数据库、R 语言或问卷设计背景的普通读者读完后能够用日常语言复述：本主题定义什么、调查原来问谁和问什么、为什么需要处理、最终变量怎样得到、哪些边界需要谨慎解释。审阅时还要逐段检查是否出现未解释的抽象词、省略对象、因果跳跃、主语静默变化，或把多个主要意思挤进一个长句。同一节包含多个并列内容时，结构应由内容关系决定：读者应能看出各部分分别讲什么、为什么放在一起、内容何时发生转换，以及最后得到什么结论。可以使用段落、标题、列表、表格或自然过渡，不设固定顺序、固定标签或禁用词。检查的是最终阅读是否连续、自然、准确，而不是是否套用了某种格式。发现问题时回到对应生成源修改并重新生成完整笔记；复核范围及未变笔记的读者审核保留条件，统一执行 [validation.md](validation.md) 的“修正后的复核范围”。

运行环境、正式生成和数据验证按数据库流程执行，不在全文文案阶段重复探查。网站发布的编辑页操作、提交前检查、失败停止和发布后边界只执行 [write-boundaries.md](write-boundaries.md)，本规范不另写第二套。同步后内容仍等待用户检查。

作者全文审阅必须保存为当前主题执行目录中的固定文件 `readability_audit.json`。先运行 `check_definition_readability.py init` 绑定当前正式笔记、正式 R、analysis_db 和 analysis_codebook；再逐项填写八个 scope。每项必须记录实际核查范围；发现问题时记录位置、原问题和修改结果，未发现问题也要说明实际读了什么，不能只填 `PASS`。未解决问题必须留在 `unresolved_issues`，并阻止普通读者检查和发布。

```powershell
python <skill-root>/scripts/check_definition_readability.py init `
  --formal-dir <主题正式目录> `
  --process-dir <主题执行目录> `
  --topic-id <NNN> `
  --note <正式笔记文件名> `
  --r-script <正式R文件名> `
  --analysis-db <analysis_db文件名> `
  --analysis-codebook <analysis_codebook文件名>
```

主题作者完成八项检查并解决所有已发现问题后，普通读者使用 `init-reader` 创建 `reader_comprehension_review.json`。普通读者与作者必须是不同任务或不同审核角色；普通读者第一遍只看最终笔记的可见文字，不读取 R、数据和作者说明。摘要首段、每个时期标签、小book提示、来源入口、每个定义变量和全文衔接都要分别保存：实际原文、自己的大白话复述、谁在什么时间发生了什么、可能怎样误解，以及最终如何处理。原文无法完整复述、对象或时间范围需要猜、指代不清或段落跳跃时，必须退回作者，不能填写通过。

作者和普通读者两份记录都完成并且没有未解决问题后，才运行 `check_definition_readability.py check`。检查器验证纯文案、作者审核、普通读者复述和四份正式成果属于同一版本，成功后生成 `publish_readiness.json`。这里的 `PUBLISH_READY` 只表示当前版本已经完成两轮检查，可以同步到网站供用户检查，不表示文案已经得到用户认可。网站同步任务开始时必须重新运行 `verify-ready`，不能用旧报告或口头回报代替。

```powershell
python <skill-root>/scripts/check_definition_readability.py init-reader `
  --formal-dir <主题正式目录> `
  --process-dir <主题执行目录> `
  --topic-id <NNN> `
  --note <正式笔记文件名>
```

```powershell
python <skill-root>/scripts/check_definition_readability.py check `
  --formal-dir <主题正式目录> `
  --process-dir <主题执行目录> `
  --topic-id <NNN>
```

机器检查不能评价文案是否好懂，也不能自动填写 `readability_audit.json` 或 `reader_comprehension_review.json`。作者检查负责事实、实现和整篇内容一致；普通读者检查负责确认最终文字能否在没有技术背景的情况下复述。风险规则中的独立核证仍只处理事实或定义风险，不能替代这项固定的普通读者检查。

## 8. 机器检查与按需验收

固定检查器负责核对以下类别，不在本规范中逐条复述全部文案规则：

1. 正式目录、唯一日志和正式输出文件；
2. raw/header/codebook、analysis、mapping、变量集合、顺序、值、缺失和覆盖；
3. 公开 R 边界、块级结构、mapping 驱动关系和禁止的后台代码；
4. 摘要、`Criteria`、detail 和笔记的结构、语义标记与源头同步；
5. 数据库周期术语、分析变量覆盖周期和概念分组；
6. 公共 helper 或模板修改后的 fixture 与代表性回归。

机器检查验证事实和结构，不用禁词、句子差异或固定话术代替可读性判断。独立验收只按 [validation.md](validation.md) 的四类入口启动；写入范围遵守 [write-boundaries.md](write-boundaries.md)。
