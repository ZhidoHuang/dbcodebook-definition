# 执行报告

执行报告用于回答四个问题：这次做了什么、每个环节用了多久、发生了哪些 Bug 或异常、任务最终停在哪里。它是过程证据，不进入正式笔记或网站正文。

## 何时创建

新建、重做或实质修改一个定义主题时，在第一次实质操作前运行 `scripts/execution_report.py init --workflow full_definition`。完整定义流程没有声明这个参数就不能作为正式执行报告。已有成果的网站同步由固定入口自动记录为 `website_only`：先用 `website-prepare` 记录本地准备和登录核对，再用 `verify-ready --start-sync` 自动结束准备、开始提交计时。只回答问题、只读查看或不改变主题成果的简短审核不创建报告。

仅修正文案或共享工具、且不改变来源和计算时，使用现有 `--workflow general` 记录实际发生的修改、生成、验证和同步，不为满足完整定义流程的角色数量而重新调查或创建无关审核。修正范围按 [validation.md](validation.md) 确定；来源或计算变化时按影响返回相应步骤；完整新建/重做用 full_definition，局部返修仍用 general，不能为凑齐角色而重做未受影响的环节。审核会话结束只证明其耗时已记录，不代表内容通过，内容是否可发布由当前成果检查和审核结论决定。

报告保存在主题执行目录：

- `execution_report.json` 是唯一事实来源，由脚本维护。
- `执行报告.md` 由同一脚本自动更新，供用户阅读，不手工填写。

已经存在执行中的报告时不得静默覆盖。继续原任务就沿用该报告；确实开始一次新的运行时，先结束旧报告并保留其真实状态。

网站入口复用同一主题仍在执行的报告；已结束报告由现有脚本归档后开始新运行。重复调用入口保留原起始时间，不重置计时。发布前核对失败不触发网站写入，准备计时继续；主执行者用 `issue` 记录实际原因。成功后用 `website-finish --result` 导入浏览器原始结果，再用 `finish` 完成收口；失败时用 `issue` 和 `stage-finish --status failed` 保留事实。

## 必须记录的环节

阶段复核交接使用 [review-start / review-result / review-check](review-roles.md#稳定输入到复核结论)，与原有 review-import 的实际角色耗时记录配合。环境不支持独立角色时，合格的隔离自查如实登记在同一报告中，不计为新建子智能体；完整流程收口认可明确披露的该例外。

完整定义流程必须使用下列五个固定 `stage_id`；每段实际工作、等待和返工都必须落在某个环节中，不能留下无法解释的长时间空档：

| `stage_id` | 包含内容 |
| --- | --- |
| `locate` | 任务定位与既有材料检查 |
| `sources` | 来源探索、权威材料核对和定义逻辑复核 |
| `download` | 最终来源选择、网页导出和文件校验安装 |
| `formal_r` | 文案定稿（环节3）、正式 R 编写/预检/复核（环节4）、成果生成（环节5）；不同工作用明确 name 分段 |
| `validation` | 结果验证（环节6）、全文与普通读者审核（环节7），分别记录 name，不混成一段 |

具备独立角色的完整流程，定义逻辑、公开 R、普通读者三个子智能体分别用 `review-import` 登记为 `定义逻辑复核`、`公开 R 复核`、`普通读者复核`，并在实际关闭后登记 `--closed`。来源不变、无需重新下载等确实没有发生的固定环节仍须登记为 `skipped`，并在 `--summary` 中说明理由；不能省略该环节或伪造几秒钟工作。完整流程缺少任一固定环节、无理由跳过环节、缺少任一审核，或任务总时间中有超过 60 秒未计入任何工作、等待或返工环节，`finish` 会拒绝完成。

用户看到的内容仍按以下九类披露；其中审核时间来自相应子智能体日志，不靠手工估算：

1. 任务定位与既有材料检查。
2. 来源探索和权威材料核对。
3. 定义逻辑只读复核。
4. 最终来源选择与下载。
5. 正式 R 编写、运行和成果生成。
6. 公开 R 只读复核。
7. 全文与普通读者复核。
8. 机器验证。
9. 已授权的网站同步。

每个环节开始时运行 `stage-start`，结束后立即运行 `stage-finish`，网站使用上述专门入口。用 `--mode work|wait|rework` 区分实际工作、外部等待和返工；进入等待或排错时结束当前段，再开始对应性质的段，不能把长时间排错全部记作“机器检查”。未传 `--model` 时，脚本按 `CODEX_THREAD_ID` 定位本任务日志，从尾部读取环节开始时的模型与推理档位；报告保留证据位置，无法核实时显示“未核实”。机器脚本或明确指定执行模型的环节仍可用 `--model` 填写，记录来源为显式声明。完成内容只写已经产生并核实的事实。

## Bug 与异常

发生以下情况时立即使用 `issue` 记录，不等到任务结束后凭记忆补写：

- `bug`：代码、规则、数据或成果存在错误。
- `abnormal`：流程偏离、工具失败、登录失效、文件状态矛盾或意外重试。
- `wait`：外部页面、下载、验证或用户操作造成的等待。

每条记录说明问题、影响、处理和当前状态：`open` 表示仍阻断交付，`mitigated` 表示交付已验证恢复但根因待修复，`resolved` 表示问题已解决。`mitigated` 必须填写恢复验证结果与剩余问题；它仍计入未解决总数，但允许以 `completed_with_issues` 收口本次交付。已经解决的问题仍然保留，不能为了让报告好看而删除。

“已解决”需要可核验的结果，例如数据包实际保存且校验通过；仅重连浏览器、换一种尝试或发出命令不算解决。绕过故障取得成果时，分清“本次交付已恢复”和“故障根因已修复”。发现历史记录误标时使用 `issue-amend` 更正并保留原因。计时跨越用户讨论或未分段排错时说明其范围，不把整段时间称为纯操作耗时。

会阻断下一步、需要用户动作或已导致重复尝试的异常，记录时同时向用户说明卡在哪、成果是否已改变和下一步动作；不等到结束才披露。一次失败先查明原因再继续，不在同一未变条件下重复尝试。

## 时间口径

审核者每次完成一批工作后，用原始子智能体日志更新当前报告，不手工估计审核耗时：

```powershell
& $Python -X utf8 scripts/execution_report.py review-import --process-dir $Process --log $AgentLog --role "定义逻辑复核"
# close_agent 实际成功后，再用同一命令增加 --closed。
# 宿主确实没有关闭工具时，已完成的最后一轮可用 --close-unavailable "实际工具限制"；不登记成已关闭。
```

只读取明确指定的子智能体日志，不扫描整个历史对话。按 agent ID 去重、turn ID 分轮，列出实际模型与推理档位、轮次数、运行时间、轮次间隔和关闭状态。两轮间隔不能当作纯审核等待或修改时间。历史复盘登记到当前复盘报告，保留原报告。完成报告需要审核已关闭，或最后一轮已完成且明确披露宿主缺少关闭工具；未完成审核仍阻止收口。

报告收口时间不等于任务最终回复结束时间。主任务收到被派发任务完成通知后，用 `turn-timing --process-dir $Process --log $TaskLog --turn-id $TurnId` 补入该完整轮次的原始起止时间；脚本单列报告初始化前、收口后的时间，不篡改原环节耗时。只读该已指定任务日志。当前轮次尚未结束时不能提前写完整耗时，报告明确显示“截至报告收口”。初始化迟了仍按下方 start-amend 补计，不能用新报告的短时间冒充整项任务历史耗时。

- 总耗时是从第一次实质操作到结束的墙钟时间。初始化迟于实际开始时，用 `start-amend --process-dir $Process --started-at <带时区的原始时间> --evidence <原始记录依据>` 补回早期时间；脚本保留更正历史，只允许向前补计，不允许向后缩短。没有原始计时依据时不估算。
- 环节耗时由脚本按开始和结束时间计算。
- 网站计时分为准备、提交和收口。`website-prepare` 从准备开始计时；`--start-sync` 自动切换到提交；`website-finish` 校验原始结果所属的运行、尝试和开始时间，以及五项质量检查和耗时，再按浏览器实际返回时刻结束提交。即使晚几分钟导入结果，也不会延长提交耗时，后续时间单列为收口。`finish` 结束收口，报告显示网站全过程。没有原始结果不能标记提交成功；失败、旧运行和错误尝试的结果均拒绝导入。
- subagent 可以并行，因此各环节耗时不能简单相加冒充总耗时。
- 不估算没有计时的历史环节；需要补记时明确写“历史阶段，未单独计时”。
- 未计时历史写进说明，不创建一个几秒钟的已完成环节冒充历史耗时。报告重新初始化会自动归档已结束运行；执行中的报告必须先如实结束，不能强制覆盖。

## 完成条件

主题宣布完成前必须满足：

- 报告状态已经结束，不是“执行中”。
- 所有实际发生的环节都有状态和完成内容。
- 没有仍阻断交付的 Bug 或异常；根因待修复项必须披露，并使用“完成，期间发现问题”状态。
- 报告列出的最终成果与本次机器验证使用的是同一批文件。

报告缺失、仍在执行、存在阻断交付的问题，或新 raw 与旧成果并存时，不能宣布完成，也不能把旧的发布就绪记录继续当作有效状态。
