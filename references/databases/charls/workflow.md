# CHARLS 变量定义标准流程

版本日期：2026-08-27

适用范围：通过 dbCodeBook 为 CHARLS 检索、裁决和定义分析变量，并生成正式数据、字典、QA、HTML、笔记和日志。

跨数据库代码与用户材料统一遵守 [common-materials.md](../../rules/common-materials.md)。本流程只补充 CHARLS 的探索、年份、来源身份、特殊编码和执行边界，不维护第二套通用规则。

正式源：本文件是 Skill 仓库中的 CHARLS 工作流；数据库稳定事实见 [profile.md](profile.md)。

## 1. 任务与目录

### 1.1 一个主题，一个定义任务

每个主题使用一个带编号和主题名的 Codex 任务：

```text
CHARLS <编号>_<主题>｜定义
```

这个任务从真实网页探索开始，负责证据核对、候选裁决后的实现、正式生成、机器检查和用户返修。同一主题的普通返修继续在原任务中完成；不要把多个主题放进固定执行任务，也不要为一次文字或代码返修另开任务。

只有以下工作单独建任务：

- 公共流程、Skill、模板或工具调整：`变量定义公共流程｜规则调整`；
- 风险规则实际触发的只读核证按 [validation.md](../../rules/validation.md) 执行；普通定义逻辑、公开R和读者复核使用只读subagent，不另建可见任务；
- 公众号、小红书或其它宣传同步使用对应下游任务。已授权的网站同步由当前定义任务继续执行，沿用同一内置浏览器页面。

研究口径、变量边界、跨期合并或公式仍需用户裁决时，定义任务在原地暂停并报告事实、影响和待决项；用户确认后仍由原任务继续。不要把“等待裁决”误作执行完成。

### 1.2 目录职责

新主题先查 `主题索引.md` 和 CHARLS 正式目录，再分配下一个主题编号。正式目录固定为：

```text
<外部配置 paths.formal_root>/CHARLS/<编号_主题>
```

过程目录保存当前主题同步形成的 `探索记录.md`、结构化来源记录和必要机器证据，不建立强制 `current_task.md`、踩坑复盘包或正式成果副本：

```text
<外部配置 paths.process_root>/CHARLS/<编号_主题>
```

`_执行线程` 在这里是文件目录名，不表示固定 Codex 执行任务。定义任务只允许写当前主题正式目录、当前主题过程目录，以及完成后需要原位更新的索引和台账。网站、生产数据、数据库脚本和其它主题遵守 [write-boundaries.md](../../rules/write-boundaries.md)，未经用户明确批准不得修改。

正式目录保留：

```text
bookapp_download.zip
raw_data.csv
raw_codebook.csv
define_charls_xxx.R
db_*.xlsx
codebook_*.xlsx
analysis_db_*.xlsx
analysis_codebook_*.xlsx
CHARLS_xxx_QA.txt
CHARLS_xxx_definition.html
CHARLS_xxx_detail.html
CHARLS_xxx_笔记.md
CHARLS_xxx_run_YYYYMMDD_HHMM.log
```

README、额外 report、closeout、定义 xlsx、`*_defined.csv`、`*_defined.rds` 和其它零散说明默认不生成。

## 2. 源头探索

### 2.1 真实网页流程

变量发现必须在 dbCodeBook 页面真实完成。不能从旧主题、旧导出、底层数据库、Parquet、问卷题号或既有 R 代码反推候选。

顺序为：

1. 从左侧目录面板进入最贴近主题的真实目录；目录筛选只是定位目录，不等于普通检索。
2. 查看目录变量表及有解释价值的下级目录。
3. 使用研究概念及常见同义词进行普通检索，发现跨目录或不同问卷项目中的同类来源。
4. 对已发现的候选，优先查阅本地官方材料，核对年份、题目文本、取值标签、适用对象、回顾期、跳转逻辑和来源文件；本地材料缺失时再查 CHARLS 官方网站。
5. 同步记录页面观察、下一步决定及候选纳入/排除理由。

不能只看 Easy label。同名或近似标签可能在不同年份对应不同题干、路径或对象，必须逐年核验官方详情和实际取值。

### 2.2 本地官方材料库

仓库内官方材料统一存放在 `references/source-materials/charls`：

- `官方问卷`：按调查年份保存家户、体检、社区、退出及死因等正式问卷；
- `技术文档`：按 `用户手册`、`发布说明`、`流程图与数据提示`、`技术代码本`、`血检资料` 分类保存。

材料文件名统一使用“调查年份 + 调查轮次或专项 + 文档性质”。正文不能确认调查年份时不猜测，可标注能够核实的发布版本年份。

dbCodeBook 仍是变量发现入口。本地官方材料用于候选发现后的事实核对，不能根据已知题号或问卷目录反向编造网页探索过程。核对时记录材料路径、年份、页码或题号，以及它确认的题义、对象、回顾期、选项、跳题或构造事实。

本地材料是默认的第一核对来源。只有本地缺少对应材料、需要确认更新版本，或需要给读者提供公开链接时，才补查 CHARLS 官方网站。官方问卷也不能代替 actual raw、raw codebook 和实际取值核对。

### 2.3 两份同步探索记录

已有主题保持用户已经核对的历史边界，不补写虚构探索史，也不事后伪造旧版检索记录。新主题及实质改动问卷范围、原题、选项或跳题呈现的既有主题，从第一次网页探索或本轮重新核对开始，同时建立 `探索记录.md` 和 schema v7 `definition_search_record.json`，分别使用 [exploration-record.md](../../../templates/exploration-record.md) 和 [definition-search-record.json](../../../templates/definition-search-record.json)。

`探索记录.md` 是直接给用户和后续复查者阅读的真实过程记录。每一步都用大白话同步写明“做了什么 → 看到了什么 → 这说明什么 → 下一步为什么这样走”，并使用 `S001`、`S002`……连续编号。它不是探索结束后的摘要，不得根据 JSON、最终 raw、正式 R 或成品笔记事后生成。

`definition_search_record.json` 是同一次探索的结构化机器记录。它不高于、不替代大白话记录，也不能作为事后生成大白话记录的事实源：

- `exploration_log` 按真实顺序记录目录、普通检索词、页面观察、官方材料、Harmonized 和文献核对，以及下一步决定和理由；每一步用 `human_step_id` 指向 `探索记录.md` 中同号步骤。
- `evidence_reviews` 记录实际查阅材料的标题、可定位位置、明确支持内容、没有说明的内容、对本轮决定的影响和对应探索步骤；不能只写“已参考”或“与文献一致”。
- `questionnaire_evidence` 逐题记录各时期正文实际呈现的官方题号、完整题干、完整选项、跳题条件与真实去向，以及本地材料路径和定位；`questionnaire_coverage` 必须覆盖每个来源组的每个时期。非问卷构造来源要明确标为不适用并说明理由。本地缺件时先记录实际查找范围和缺口，才能补用官方网站，不得用 Easy label 或解释性分支名称代替问卷证据。
- `candidate_decisions` 记录候选研究概念、纳入/排除结果、理由和对应探索步骤。
- `source_groups` 汇总最终来源并指回探索步骤，同时记录各周期题义、对象、回顾期、记录方式的共同点与差异，以及最终合并或分开的理由；不能只列变量名，也不能代替探索日志。
- `definition_plan` 在写 R 前逐个记录正式变量的研究含义、采用哪些来源组、怎样构造，以及缺失和跳题怎样处理；它是既定方案，不是代码写完后的反向概括。
- 每个正式 raw 必须能追溯到已记录来源和纳入理由。
- 后补记录必须标为回溯核对，只证明当前来源可复现，不冒充最初探索过程。

两份记录必须来自同一步真实网页操作并保持对应。发现内容不一致时，回到页面事实和当时记录核对，不默认任何一份自动覆盖另一份。探索中的阶段性结论和待决问题应直接用大白话向用户汇报；不得只留下 JSON 或内部状态码让用户自行查找。

周期断层、同名不同义、题义变化、公式不完整、来源身份不明、重复计入风险、命名不清或其它会使某个定义变量本身无法确定的逻辑漏洞一经发现，立即向用户报告事实、影响和待裁决项；未裁决前不得进入正式生成。不同原始题目之间的回答互相矛盾，但每个定义变量仍能按自己的直接来源忠实生成时，不属于自动待裁决项；按本流程的原始矛盾默认规则记录后继续。

## 3. 候选与研究口径

### 3.1 文献调研

完成网页探索和初步候选后、下载 raw 前，按研究问题需要进行文献调研。简单单题可简要确认常见定义；量表、认知测验、指数、总分、复合变量、跨期项目变化或存在计分歧义时必须实质调研。

证据顺序为：

1. dbCodeBook 的真实目录、普通检索和候选页面，以及实际 raw 和 raw codebook；
2. 本地官方材料库中的正式问卷、用户指南、技术文档和可定位构造过程的 Harmonized CHARLS 技术代码本；
3. 本地缺件、版本核对或公开引用所需的 CHARLS 官方网站材料；
4. 原始量表、方法文献、正式指南、共识、制度和主管机构文件；
5. 明确报告可复核题项、周期、公式和缺失处理的高质量直接研究；
6. 一般应用研究。

正式发表不自动等于权威。每个实际采用的来源要记录其样本/周期、研究概念、项目或 raw、公式、范围、完整性处理，以及它支持本轮候选的哪一部分。来源未报告的内容明确记为未报告，不根据结果或上下文补全。

每次官方材料、Harmonized 或文献核对都作为真实探索步骤，按发生顺序写入 `探索记录.md` 的 `Sxxx`，并在 `definition_search_record.json.evidence_reviews` 登记同号步骤。记录必须直接说明“材料写了什么、没有写什么、因此本轮怎样决定”，不能在笔记完成后根据最终文案反向补造调研记录。

当 Harmonized CHARLS 已提供同一或高度相近的研究概念时，设计正式变量前先记录其变量名、概念边界、分类和构造方法，把它作为优先的方法学参照。正式变量仍须由本次网站下载的原始问卷字段重建；完全采用、部分采用或不采用 Harmonized 口径，都要明确写出对应关系和理由，不能只把 Harmonized 放在末尾当作泛泛核对材料。

必须区分：来源明确陈述、可由官方题目/raw 直接核实的事实、本项目拟采用方案。影响变量含义、公式、跨期可比性或缺失处理的证据缺口进入用户裁决，不由执行任务自行填补。

### 3.2 原始题目间矛盾的默认处理

当同一受访记录在不同原始题目之间互相矛盾时，默认忠实保留，不替受访者判断哪道题正确。各定义变量按自己的直接来源分别生成；例如筛选题明确回答 No 时，状态变量可为 0，而另一道金额题同时记录正金额时，金额变量仍保留该正金额，允许最终出现“状态为 0、金额大于 0”。

除非用户明确裁决，不得为了让定义变量内部一致而采用筛选题优先、金额题优先、强制补 0、改缺失、删除金额、排除记录或覆盖任一原始答案。发现矛盾后应报告涉及题目、周期、方向、数量和具体表现，在过程目录保存可复核的冲突记录。生成规则写入相关变量的 `定义逻辑`；只影响单个变量时由该变量的 `注意点` 说明，同时影响多个变量或整个主题时再由小book提示说明总体边界。

原始题目间矛盾若可按直接来源分别忠实生成，不阻断正式定义，也不自动进入 `RESULT_REVIEW_REQUIRED`。只有某个定义变量本身无法确定怎样从直接来源生成，或存在来源不明、重复计入、同一变量多来源覆盖规则不明等实质定义问题时，才进入用户裁决。

### 3.3 主题独立性与可研究性

正式编号和目录创建前完成：

- 与已有分析变量比较研究含义、原始来源、构造逻辑和实际取值；逐值相同或只是改名时复用已有主题。
- 只是已有变量的比例、合计或二分类等直接派生时原则上并入原主题；形成独立研究概念或解释边界时才单列。
- 按候选基线年份报告独立受访者有效人数，不用全部人次或多波次合并行数判断价值。
- 计划纵向研究时，再按个人 ID 评估进入后续波次的人数；已有结局时同时看结局有效人数或事件数。

候选结论只有 `NEW`、`MERGE`、`REUSE`、`DEFER`。只有 `NEW` 且口径已经裁决时分配新编号。

### 3.4 周期完整性

按预期调查周期列出每个研究概念的来源覆盖。前后周期存在而中间缺失时暂停下载并回查目录、普通检索和官方问卷，只允许形成：

- `QUESTION_NOT_ASKED`：该周期确实没有对应题目；
- `MEANING_CHANGED`：存在相关题目，但题义、对象或参考期不能直接连接；
- `SOURCE_OMITTED`：来源存在但候选遗漏，补齐后重新预览和下载。

两端自然缺少题目不自动视为错误，但必须在用户材料中准确说明正式覆盖与解释边界。

研究概念、官方问卷或 Harmonized 方法已经确认某组来源属于完整定义时，如果当前候选或下载没有包含该来源，只能记为 `SOURCE_OMITTED` 并退回网页补选、重新预览和下载。不得为了迁就现有 raw 而自行缩窄研究概念、样本人群或正式变量范围，也不得保留上位主题名称却只定义其中一个子人群。确有研究理由改做更窄概念时，必须先向用户说明缩窄后的对象、覆盖损失和用途，取得裁决后再继续。

## 4. 选择、预览与下载

### 4.1 选择身份

每个候选标明角色：

- 直接来源：当期核心回答；
- 预载或上一轮来源：只在已经裁决的条件下补充；
- 辅助来源：用于筛选、路由、完整性或 QA；
- 排除来源：保留排除理由，不进入下载。

来源别名的成立条件、下载前命名、完整变量族和展示简称统一执行公共规范第 1.2 节。CHARLS 在页面选择变量时落实已经确定的最终别名，并把需要完整核对的模式和编号范围登记在 `definition_search_record.json` 的 `alias_families` 中；下载前的来源检查会据此拦截缺项或中途换后缀。

### 4.2 预览

把网页最终选择顺序逐行写入当前执行目录的 `download_selection.txt`，一行一个最终别名。该文件只保存这一次准备下载的变量，不写说明文字，也不另抄第二份变量清单。

点击下载前，先用来源检查器核对 `download_selection.txt` 与 `definition_search_record.json`：两者变量集合必须完全一致；网页顺序可以不同于来源分组顺序。检查不通过时回到网页补选或清理候选，不先下载再补解释。

```powershell
python <skill-root>/scripts/check_definition_source_record.py `
  --record <definition_search_record.json> `
  --selection-file <download_selection.txt> `
  --topic-id <NNN>
```

预览同时确认：

- 变量数、变量顺序和别名；
- 每个重复变量族至少核对首项、中间项和末项，确认词干、编号和后缀始终一致；
- 记录数和数据层级；
- `ID`、`id`、`year` 及当前数据层级所需身份列；
- 筛选题、跳题条件和所有正式计算来源均已纳入；
- 不应进入的候选没有混入。

身份列必须服从最终数据层级，不能机械沿用原始表结构。CHARLS 原始长表一行代表“某人某一期”时，大写 `ID` 用作人期记录键，小写 `id` 用作受访者键；若分析结果已经长转宽为“每名受访者一行”，小写 `id` 即为唯一键，不再把任一期的大写 `ID` 接入宽表。只有结果仍保持人期、家庭成员期或其它重复记录层级时，才保留相应的记录级唯一键。正式生成前必须同时核对输出层级、唯一键和保留的身份列。

读取 CHARLS raw 时，可能带前导 0 的个人、家庭和社区身份列必须按字符读取。机器闭环不仅核对身份列名称和唯一性，还要确认分析输出中的共同身份组合确实存在于 raw，防止前导 0 丢失或产生不存在的身份值。筛选、排序或长转宽可以改变行数和顺序，因此不能机械要求分析输出与 raw 逐行等长对应。

### 4.3 落盘

配置的 dbCodeBook 页面完成选择、预览并下载后，使用 `<skill-root>/scripts/recover_dbcodebook_export.py --archive <本次下载包> --database charls --out <正式主题目录> --expect-vars-file <download_selection.txt>` 复用同一份变量清单，保存并核对本次 zip/raw。不要在恢复命令中重新手抄变量。

无论来源，正式定义只使用本次页面确认并实际落入正式目录的 `bookapp_download.zip`、`raw_data.csv` 和 `raw_codebook.csv`。恢复或下载报告记录来源和匹配结果即可，不再写过程卡或复盘包。

**数据来源硬边界：定义所用 raw 变量必须全部来自本次 dbCodeBook 网站选择并下载的数据包。** 不得从本地 DTA、Parquet、旧下载包、既有主题数据、Harmonized 数据或其它数据库文件补列、拼接、替换或重建网站未下载出的 raw。官方问卷、技术代码本和本地正式数据只能用于事实核对，不能作为正式 raw 的替代来源。若网站未能完整下载已确认的变量清单，立即停止正式定义并报告下载缺口；修复网站选择或下载后重新下载，不能用线下补构绕过。

**重新下载只由来源变化触发。** 只要最终来源清单发生任何变化，包括新增、删除、替换来源，调整周期、文件、来源身份或整组别名，就必须回到网站，按改变后的完整清单重新选择并一次下载。不得从旧包筛列，也不得把旧包与补充下载拼成新的正式 raw。反过来，如果最终来源清单没有变化，只改文案、展示、代码注释、主题编号，或在同一批 raw 上调整实现方式，不机械重新下载。

正式 R 运行前，来源检查器直接核对三组事实：`definition_search_record.json` 中的最终来源必须与 `raw_codebook.csv` 一致；正式目录中的全部 `raw_data*.csv` 和 `raw_codebook.csv` 必须与同目录 `bookapp_download.zip` 内的 CSV 逐行、逐单元格一致；R 使用的来源必须与前两者一致。任一不一致都直接停止。检查只忽略 UTF-8 BOM 和换行格式差异，不修改或标准化文件。这个检查不看主题新旧，也不另造主题凭证。

## 5. CHARLS 正式 R

### 5.1 开工闸门与通用代码合同

正式 R 开工前，以下内容必须已经由网页探索、官方材料、实际 raw 和必要裁决确定：

1. 研究概念、正式变量和变量关系；
2. 各周期采用的来源、题义、对象、回顾期和记录方式；
3. 跨周期来源哪些方面一致、哪些方面不同，以及合并或分开的理由；
4. 编码分组、跳题、结构性 0、特殊缺失和计算公式；
5. 已发现的原始题目间矛盾怎样分别忠实保留、记录和披露；
6. 不存在仍会改变定义结果的未决问题。

正式 R 只解释并实现上述既定方案，不承担寻找规律、比较候选方案或现场决定研究口径的任务。来源选择、合并或区分、编码映射、阈值、跳题、缺失和公式等处理决定必须先于正式代码及其中的验证输出形成；验证只能确认既定判断，不能在运行后首次生成研究口径。发现任一项仍不清楚时，立即退回相应探索或裁决步骤，不用公开代码边写边猜。

如果本轮改变分析变量集合、调查对象、周期、问法、组成关系或缺失处理，还必须先完成 `definition_change_impact.json`。其中每个改变的问卷题组都要指向官方材料和正式成果目录 `文案.md` 中已经写出的代表性原题或明确标注的概括；不能先写 R、生成笔记，再回头补一张影响表。

包头、公开代码边界、读者背景、`recode.chr()`、`recode.num()`、`yyds_coalesce()`、mapping、命名和用户材料统一遵守公共规范，不在本流程复述。

CHARLS 补充要求：

- `year` 的生成与使用必须来自实际数据身份；不为展示波次范围创建纯副本变量。
- raw 确有非目标调查年份时，只在正式输出边界按研究范围排除，不把样本筛选伪装成读取步骤。
- 家户来源缺少个人 `id` 时，只有在数据层级和派生规则已经核实后才生成；不使用防御式猜测分支。
- 数据类型、取值范围、年月配对或特殊编码等问题必须先检查实际 raw。确认存在问题后，才按已经说明的规则转换或清理；实际数据没有该问题时直接使用原值，不加入无效的 `as.numeric()`、静默补缺失或假设性清理。需要防止以后数据变化时，应检查并明确报错，不得一律先改值。
- 正式写出使用 `write.xlsx(..., overwrite = TRUE)`，保证四张工作簿同步刷新。

### 5.2 特殊编码

时间、频次、金额、时长、计数、总分和连续换算变量必须检查 `997`、`998`、`999` 等高位值。

- 结合官方问卷详情、raw codebook 和实际分布判断它们是特殊编码还是合法数值；
- 未确认前不得进入连续计算、均值、总分、时间换算或计数；
- 特殊编码按题义处理并在 QA 报告出现次数和处理方式；
- 合法真实值保留时记录依据；
- 分类变量也要核查这些值是否为拒答、不知道、不适用或其它特殊选项。

### 5.3 Mapping

`add_mapping()` 追溯到全部参与定义的 raw 来源。中间派生变量可以同时保留，但不能替代 raw 来源；中间变量即使不在 raw codebook 中，也不能因为匹配不到标签而从 `processed_vars` 或 `original_vars` 丢失。

## 6. 正式输出与用户材料

主交付为四张 xlsx：

- `db_*.xlsx`：当前数据层级的完整数据与定义变量；
- `codebook_*.xlsx`：完整变量说明；
- `analysis_db_*.xlsx`：身份列和正式分析变量；
- `analysis_codebook_*.xlsx`：正式分析变量字典。

同时生成 QA、definition HTML、detail HTML、完整笔记和唯一成功日志。definition 表在 R 内存中生成，不使用 definition xlsx 中转。

完整笔记结构为：

```text
## 摘要导读
## 定义
（如有文献，紧接定义表）
## 定义的组分概览
## 定义的组分详情
## 材料
### 1-提取变量
### 2-代码材料
```

- 摘要、`Criteria`、提取变量、公开 R 和 detail 分组分别从正式生成源同步。
- “定义的组分概览”和“定义的组分详情”由 detail 片段自身提供；笔记拼装器直接嵌入该片段，不得在外层额外添加同名标题。最终笔记各保留一个标题，不能形成“详情 → 概览 → 详情”的重复结构。
- `1-提取变量` 包含非空、可直接粘贴到网站批量输入框的 `网站完整原始变量身份=下载别名` 列表和一个 `Go to 提取变量` 按钮。左侧保留 CHARLS 网站显示的模块括号，右侧使用最终下载别名；完整格式和三类变量关系的边界按公共规范第 1.2 节执行。
- `2-代码材料` 截取正式 R 到 `# 输出` 之前；不放 QA、HTML、笔记拼装或可视化 helper。
- detail category 按真实概念显式分组，每组 source 在前、defined 在后；未匹配项进入 `Other / check` 并触发 QA。
- 用户材料内容、格式和可读性全部引用公共规范，不在 CHARLS 流程中另列检查词和固定句式。

## 7. QA 与机器闭环

### 7.1 业务 QA

- 关键 raw 按年份查看真实取值和特殊编码；同名漂移只在适用年份核对。
- 每个分析变量按年份检查非缺失、缺失和分类/范围；中间年份骤降必须解释为问卷路由、来源遗漏、定义过严或原始数据事实。
- 历史状态变量核查 non-current 人群是否存在既往来源，不能把当前不发生直接解释为从未发生。
- 四张工作簿重读后核对行列、身份列、变量顺序、值、缺失、mapping 和 codebook。

### 7.2 正式运行

依赖安装和正式运行分开。只有新环境、缺包或明确需要更新 `dbCodeBookr` 时，才单独运行 `setup_definition_environment.ps1`；正式定义运行期间不联网安装或更新 R 包。

使用当前 Skill 根目录的 `scripts/run_r_definition.ps1`，在 PowerShell 7 中直接读取本机配置并从头正式运行。正常运行已经先检查公开代码合同、已安装包、来源记录、下载代码本和下载凭证，预检通过才进入 R，不需单独重复预检。只有本次目的就是检查运行条件、不生成成果时才加 `-PreflightOnly`。runner 和 checker 都使用当前 Skill 的脚本，验证读取本次正式目录，不调用演示目录、旧仓库或旧临时数据副本。

正式运行默认最多 30 分钟，日志分别记录静态检查、包检查、来源检查和 R 执行耗时。超时或失败后停止并查看该次错误，不自动重跑；修正明确原因后再由人工发起下一次正式运行。临时片段、环境探针或改写副本不能代替正式运行。

### 7.3 收口

收口依次完成：

1. 正式 runner 成功，目录只保留一个含退出码 0 的最终日志；
2. 固定检查器和按改动范围所需的回归/复算通过；
3. `探索记录.md`、`definition_search_record.json`、恢复报告、自检报告和必要裁决证据存在且可读；
4. 对最终版运行 `check_definition_readability.py init`，由作者生成绑定当前笔记、正式 R、analysis_db 和 analysis_codebook 哈希的 `readability_audit.json`；作者完成后，再由不同审核角色运行 `init-reader`，只阅读最终笔记并填写 `reader_comprehension_review.json`；
5. 当前主题任务按通用规范从头到尾通读最终笔记和公开 R，逐项填写八个 scope；发现问题时修改生成源、正式重生，并重新初始化和完整通读，不能复用旧审核；
6. 运行 `check_definition_readability.py check`，验证纯文案、作者审阅和四份成果属于同一版本；通过只表示当前版本可以同步网站；
7. 当前主题到达可发布状态后，进入网站检查同步阶段，按 [write-boundaries.md](../../rules/write-boundaries.md) 完成 `verify-ready`、网站提交、主题索引和验收台账更新；数据库流程不复制网站控件、超时、失败恢复或发布后检查规则。网站返回文章详情页后状态记为 `USER_REVIEW_PENDING`；
8. 报告哪些用户可见表面发生变化，以便宣传任务单独同步；
9. 用户确认后，把同一主题状态更新为 `COMPLETE`。

默认状态为：

```text
DISCOVERY -> DEFINITION_READY -> GENERATED -> MACHINE_CHECK_PASS
          -> AUTHOR_FULL_TEXT_REVIEW -> ORDINARY_READER_REVIEW -> PUBLISH_READY
          -> USER_REVIEW_PENDING -> COMPLETE
```

`PUBLISH_READY` 表示作者检查和普通读者检查都已完成，检查器确认纯文案、两份审核记录和四份成果属于同一版本，可以同步网站；它不表示用户已经认可内容。成果变化后的复核和审核保留条件统一执行 [validation.md](../../rules/validation.md) 的“修正后的复核范围”。网站同步后进入 `USER_REVIEW_PENDING`，只有用户确认才进入 `COMPLETE`。机器检查通过只表示事实和结构检查完成，不能代替两轮阅读。

## 8. Profile 边界

CHARLS 数据库级稳定入口、全局数据特征和跨主题核验要求写入 [profile.md](profile.md)。具体主题的 raw 清单、变量名、公式、阈值、冲突、文案和历史裁决保留在正式主题与其机器证据中，不回填标准流程或 profile。
